# T8: The real V4L2 media-controller driver for MT6785 SENINF + CAMSV

State on the tablet before T8: with the experiment modules
(`drivers/staging/yt11-cam/`, `mt6785-seninf-tm` / `mt6785-camsv-tm` /
`yt11-cam-probe`) and the userspace sequence `tools/camera/ov-cap.py`,
the OV8856 on CSI port 1 delivers full 640x480 RAW10 frames into memory
through MUX2 -> CAMSV0 (docs/hardware/CAMERA.md "First frames").
T8 turns that into a proper driver pair so `v4l2-ctl` / `media-ctl` and
later libcamera's simple pipeline can capture.

## 0. First-boot postmortem (2026-11-16, logs/t8-first-boot.txt)

Two failures, both fixed:

1. **`mt6785_camsv` failed with `WARNING at media_create_pad_link` and
   "failed to link video node: -22"** — the video device entity was
   never given a pad: `camsv_video_register()` called
   `media_create_pad_link(sd, 1 -> vdev, 0)` but never ran
   `media_entity_pads_init(&vdev->entity, 1, sink_pad)` first, so
   `num_pads == 0` and `sink_pad 0 >= num_pads` fails with -EINVAL
   (mc-entity.c WARN).  Fix: a `vdev_pad` (MEDIA_PAD_FL_SINK) in
   `struct mt6785_camsv`, `media_entity_pads_init()` on the video
   entity before `video_register_device()`, and
   `media_entity_cleanup()` on the unregister path.
   Additionally the SENINF entity needed
   `.get_fwnode_pad = v4l2_subdev_get_fwnode_pad_1_to_1`: without it
   the media core's default lookup returns the FIRST sink pad, so a
   sensor wired to port 1 would be silently linked to pad 0.
2. **No sensor bound**: `i2c 2-0036: deferred probe pending: supplier
   regulator-vcamd not ready` — the three fixed regulators all had
   `pinctrl-0 = <&cam_gpio_pins>` (5 pins); a pinctrl state is
   exclusive per device, so the second regulator's probe failed with
   -EBUSY and never registered, deferring the ov8856 client forever.
   Fix: no `pinctrl-0` on the regulators (regulator-fixed muxes its
   own `gpio` through gpiod) and `camera-probe` (M0 node claiming the
   same GPIOs) set to `status = "disabled"`.  Binding failures now
   print through `dev_err_probe` (endpoint parse, larb maps, clocks).

The new frame-layout facts of that session (12-bit containers from the
begonia FMT_SEL/PAK values, the le10 bitstream with 0x102/1, 481
lines at 640x480, FBC re-arm per frame) are folded into sections 2.2
and 3.

## 0b. Second-boot postmortem (2026-11-17, logs/t8b-streamon.txt)

Good: no defer, sensor bound on port 1, /dev/video0 and subdev nodes
exist.  Two problems, both fixed:

1. **No seninf→camsv link**: `seninf_notifier_bound()` created it with
   `v4l2_create_fwnode_links_to_pad(&s->sd, ...)` — but that helper
   iterates `src_sd->fwnode`, which is only assigned by async
   registration (`__v4l2_async_register_subdev`), and the SENINF
   subdev registers directly under its own v4l2_device.  With
   `fwnode == NULL` the endpoint loop silently did nothing (returned
   0), leaving both halves unlinked; `start_streaming` then hit
   `no SENINF connected` (-ENOLINK) and — because the error path did
   not return the queued buffers — the `vb2_start_streaming` WARN,
   surfaced to userspace as `VIDIOC_STREAMON: Link has been severed`.
   Fixes: create the link directly with `media_create_pad_link(seninf
   pad 3 -> camsv pad 0, ENABLED|IMMUTABLE)` in the bound callback
   (the DT endpoints already pair them), set `sd->fwnode` explicitly
   at probe, and on any `start_streaming` error return all queued
   buffers (`VB2_BUF_STATE_QUEUED`) before stopping the pipeline.
2. **Ambiguous entity names / script**: the camsv subdev and the video
   node were both "mtk-mt6785-camsv", so the script resolved the
   "capture entity" to the subdev (`/dev/v4l-subdev2`, prefixed into
   the broken `/dev//dev/...`) and passed the macro name `SBGGR10P`
   where v4l2-ctl wants the fourcc characters `pBAA`.  The video
   entity is now named **"mtk-mt6785-camsv video"** and the script
   matches the exact entity name, formats every pad (sensor 0,
   seninf 1 and 3, camsv 0 and 1) and uses `pixelformat=pBAA`.
   Also: default formats on all subdev pads are now the coherent
   validated geometry (SBGGR10_1X10 640x480, matching the ov8856
   24 MHz mode), and both drivers' `link_validate` promote the
   core's dev_dbg mismatch report to dev_err naming pads and formats.

## 0c. Third-boot state and fixes (2026-11-17, it streams)

Streaming works end to end: complete media graph, 20 buffers returned,
a real decoded picture.  Follow-ups, all in this iteration:

1. **Multi-buffer rotation** was broken: the DMA kept writing the
   stream-on address, so only every 4th v4l2-ctl buffer had data.
   The IMGO BASE_ADDR must be reprogrammed per frame *before* the
   FBC re-arm (ov-cap.py `arm_one_frame()` order: BASE_ADDR, FBC_EN,
   FBC_EN|RCNT_INC — the address is latched by the arm, not read
   continuously).  The driver now keeps an explicit `active` buffer
   (the one whose address was latched last), completes exactly that
   one on PASS1_DON, and arms the next queued buffer.  (The torn
   first-frame heuristic of this pass was replaced by a warm-up
   frame, see 0e item 5.)
2. **Script media-ctl -EINVAL**: setting the seninf/camsv subdev pad
   formats by hand is unnecessary (they are pass-through and default
   to the sensor mode) and one of those calls was what failed.  The
   script now formats only the sensor pad (by detected entity name)
   and the video node, and adds `-s WxH`, `-e EXPOSURE`, `-g GAIN`,
   `-t` (test pattern).
3. **Large modes**: 1632x1224 and 3264x2448 (ov8856 24 MHz 2-lane)
   flow through the pipeline unchanged — geometry is pass-through,
   buffer size follows `sizeimage = BPL * height`.  The DPHY HS-settle
   stays at the validated 15 for every link frequency (the scaling of
   this pass was dropped, see 0e item 3), overridable with the
   `hs_settle` module parameter.
4. **debugfs status dumps** (no /dev/mem needed):
   `/sys/kernel/debug/mt6785-seninf-status` (ANA cal status, CSI2
   IRQ/LINE_FRAME/PACKET_CNT, DPHY lane FSMs, MUX and CAM_MUX sizes
   for the active port — the ov-cap.py values) and
   `/sys/kernel/debug/mt6785-camsv-status` (INT_STATUS, TG_FRMSIZE,
   FBC_CTL2 frame count, IMGO base).  Both power the CAM domain for
   the read.
5. **Second sensor**: an S5K4H7 node (`camera-sensor@2d`, T7 driver)
   on `&i2c4`, endpoint on seninf CSI port 0 for now (its true port
   is unknown; moving it is a one-line change on each side — see the
   DT comment).  The seninf now supports several bound sensors and
   routes the one whose link is enabled (see 0d for the selector
   rules); the shared vcama/vcamd rails are handled by the regulator
   framework's reference counting.

## 0d. Fourth-boot postmortem (2026-11-17, two sensors broke streaming)

Both sensors probed and bound, debugfs worked, but nothing could
stream: with two ENABLED|IMMUTABLE sensor links the pipeline walk
validated BOTH links against one source pad —
`seninf:3 -> camsv:0 ... 0x300a vs 0x3007` (SGRBG vs BGGR), then the
idle sensor's link mismatched too, and the seninf source format
followed whichever sink was set last.  All three symptoms are one
design error: the selector was not a selector.

Fix — the seninf is now a proper input selector:

- sensor->seninf links are **dynamic** (no IMMUTABLE); exactly one may
  be enabled at a time.  `link_setup` refuses a second enabled link
  (-EBUSY, with a dmesg line naming both ports) and any link change
  while streaming; switching sensors is disable-then-enable.
- the link on port 1 (OV8856, the hardware-validated camera) is
  created enabled; every other sensor's link is created disabled.
- the source pad format always **mirrors the enabled sink pad**
  (`seninf_sync_source_fmt`): on every sink set_fmt and on every link
  change.  Setting the source pad directly is rejected (-EINVAL).
- only the enabled link is walked by `media_pipeline_start` (disabled
  links are skipped by the core), so the idle sensor's format no
  longer matters.
- the camsv video node's S_FMT now pushes the matching bus code onto
  the camsv subdev pads, so choosing the Bayer order through the
  fourcc keeps link validation happy without touching media-ctl.
- the script drives it all: `-c ov8856|s5k4h7` switches the link,
  reads the sensor's actual bus code with `media-ctl --get-v4l2`,
  propagates it to the seninf/camsv pads, picks the matching fourcc
  (pBAA/pgAA/pGAA/pRAA) and passes `--bayer` to raw2rgb.py.

## 0e. Fifth-boot postmortem (2026-11-17, no media device: -ENOLINK)

Log: `s5k4h7 4-002d bound on port 0`, then `no unique sensor pad on
port 0`, `error -ENOLINK: failed to register async notifier`, seninf
probe failed with -67, so no `/dev/media0` at all.

**Cause**: the bound callback created the sensor link and then looked
the sensor's pad up through that link with
`media_pad_remote_pad_unique()`.  That helper (like
`media_pad_remote_pad_first()`) only considers ENABLED links
(`mc-entity.c`: `if (!(link->flags & MEDIA_LNK_FL_ENABLED)) continue;`
then `-ENOLINK` when nothing is found).  The S5K4H7 link is created
disabled on purpose (selector design, 0d), so the lookup failed, the
bound callback returned -ENOLINK, and because the S5K4H7 was already
registered the error came out of `v4l2_async_nf_register()` in probe.
The OV8856 (port 1, link created enabled) would have passed.

**Fix**: the sensor's source pad comes from the endpoint the async
connection matched (`asc->match.fwnode` is the sensor-side endpoint):
`media_entity_get_fwnode_pad(&sd->entity, asc->match.fwnode,
MEDIA_PAD_FL_SOURCE)` (pad 0 on both the ov8856 and the s5k4h7, which
have a single source pad), then `media_create_pad_link(sensor:pad ->
seninf:port, port == 1 ? ENABLED : 0)` directly.  This also drops
`v4l2_create_fwnode_links_to_pad()`, which returns 0 without creating
anything when the endpoints do not match.  The bound callback logs
`port N: link from <sensor>:0 enabled (selected)` or `... disabled`.

Other defects found in the unfinished pass, fixed in the same change:

1. **Wrong source format on a link switch**: the media core calls
   `link_setup` BEFORE it updates `link->flags`, so the "enabled port"
   scan inside `link_setup` still saw the old state and the source pad
   copied port 1's format when port 0 was being enabled.  The port
   being enabled is now taken from the `local` pad.  A sink `set_fmt`
   only updates the source when it targets the selected port; setting
   the source pad returns its (mirrored) format instead of -EINVAL.
2. **WARN on every stream-on**: the LINK_FREQ control of both sensors
   is an integer menu, and `v4l2_ctrl_g_ctrl_int64()` WARNs on any
   type other than INTEGER64 (and returned 0).  The driver now uses
   `v4l2_get_link_freq()`, for the debug log and the status dump only.
3. **HS-settle back to the validated 15 for every link frequency**:
   the 1/f scaling gave 8 at 645 MHz, below the D-PHY window its own
   comment computed ([9,15] at 1290 Mbps/lane).  The window
   [85 ns + 6 UI, 145 ns + 10 UI] is dominated by its fixed part (its
   centre moves under 5 % from 720 to 1400 Mbps/lane), so the
   validated value is kept; `hs_settle=` remains the sweep knob.
4. **Arm race**: the frame-done IRQ armed the next buffer after
   dropping the lock, while QBUF could arm another one at the same
   time on a second CPU (one of them lost, never returned to vb2).
   Both paths armed under `buf_list_lock` in this pass; since 0f
   only the interrupt thread arms (`camsv_arm()`).  Stop and
   start-failure paths `synchronize_irq()` after disabling the
   hardware.
5. **First frame**: the pass armed the first buffer before the TG ran
   and flagged it torn when INT_STATUS bit 7 ("SOF", a guess) was set.
   That bit is set at every frame end (0x0009048f on good frames), so
   the first buffer would always have come back as an error.  The
   driver now follows ov-cap.py: TG started with FBC_EN alone, the
   first arm on the first PASS1_DON (a warm-up frame, which the t8c
   driver already proved fires without RCNT_INC), so a TG started
   mid-frame tears no buffer.  The sequence counter advances on every
   PASS1_DON, so the first delivered buffer is sequence 1 and dropped
   frames show as gaps.  IMGO_BASE_ADDR is set to the first queued
   buffer at configuration (it was 0).
6. CAMSV `v4l2_subdev_init_finalize()` now runs before
   `v4l2_async_register_subdev()` (the notifier can bind the subdev
   from inside that call).
7. **Script**: the "disable other links" loop matched
   `" [ENABLED` while media-ctl prints `":0 [ENABLED]`, so it never
   disabled anything (enabling the S5K4H7 would then fail with
   -EBUSY); it also took the sensor's pad number for the seninf pad
   and word-split entity names at their space.  The script now
   parses every seninf sink link (pad heading, sensor, sensor pad,
   enabled) and handles names with spaces; it keeps the sensor's own
   bus code in the mode request, sets controls after the mode (a mode
   change resets the exposure range), and extracts the last frame
   with one `dd bs=<frame>` (`bs=1` took minutes at 3264x2448).

## 0f. Sixth-boot postmortem (2026-11-17, interrupt storm, one buffer)

Probe clean, script end to end, but `v4l2-ctl --stream-count=20`
(640x480, test pattern): buffers 0..3 done within 20 us (seq 1-4),
then one buffer every ~0.95 ms with seq jumping by ~550 ("fps:
575000, dropped: 549"); only buffer index 0 ever held data, and only
55-154 non-zero samples.  CAMSV after the run: TG_FRMSIZE 640x481,
FBC_CTL2 0x03000001, IMGO_BASE 0xfe100000.

**Storm cause: INT_EN = 0xffffffff set INT_WCLR_EN.**  INT_EN reads
back 0x803b04ff after a 0xffffffff write (begonia
`camsv/frames/d1-run.txt`): bits 0-7, 10, 16, 17, 19-21 and **31**
exist.  In the ISP4/5 CAMSV layout bit 31 is INT_WCLR_EN, which turns
INT_STATUS from read-to-clear into write-1-to-clear.  The handler only
read the status, so the level-low line never dropped: ~575000
interrupts a second (the CPU's limit), each one seeing PASS1_DON
again.  The vendor HAL writes 0x001304b1 (VS1, TG_ERR, TG_GBERR, SOF,
PASS1_DON, IMGO_ERR, IMGO_OVERR, SW_PASS1_DON, bit 31 clear) and so
does the driver now.  The handler also writes the status back (clears
it in write-clear mode, ignored in read-clear mode), config drops any
pending status, and a storm guard masks INT_EN with a dmesg error
above 10000 interrupts in one second.  The committed t8c driver wrote
the same 0xffffffff, so it must have stormed too: it never showed
because it numbered only completed buffers, so there were no sequence
gaps.

**Rotation: no per-frame IMGO address on this hardware so far**
(superseded by 0g: the DMA only ever wrote one frame per stream, so
this was never really tested).
Every capture since t8c put data only in the buffer whose address was
programmed before the TG started.  This was true with BASE_ADDR
rewritten after PASS1_DON (t8c, the ISP3.0 driver's method, with
MODULE_EN DB set) and before each FBC arm (t8f).  `ref/isp30` (MT8365)
has no address ring: it writes BASE_ADDR in the PASS1_DON handler.
Nothing reachable describes the vendor's MT6785 per-frame update (the
HAL lift only names `DMAO_CAMSV_B::setBaseAddr` and "enqueue |= 1").
The driver therefore defaults to a **bounce buffer**: the DMA always
writes one driver-owned buffer (`dma_alloc_noncoherent`, cacheable,
contiguous, below 4 GB). The threaded interrupt handler copies each
complete frame into the next vb2 buffer and only then re-arms the FBC.
While it copies, the FBC drops frames, so a frame is never overwritten
mid-copy (at 3264x2448 the ~10 MB copy may halve the frame rate).

**Only whole frames are delivered**: before each arm the driver writes
a 16-byte marker at the start and at the end of the target.  At
PASS1_DON a frame counts only if both were overwritten.  If the tail
is intact the frame went elsewhere or was dropped ("missed": stay
armed, give up after 4).  If the head is intact but the tail was
written, the DMA started mid-frame ("torn": re-arm).  This works
whatever the FBC counters mean.  Arming happens right after PASS1_DON
(vertical blanking); the first arm of a stream happens at its first
VS/SOF, and a frame torn by that is caught by the markers.  The
sequence number is the index of the PASS1_DON that ended the frame,
so gaps are real dropped frames.

`rotate=1` (`/sys/module/mt6785_camsv/parameters/rotate`, read at
each STREAMON) keeps the per-buffer BASE_ADDR path, with the same
markers in each vb2 buffer.  If BASE_ADDR does not latch, those
buffers come back with an error and the debugfs `missed`/`gave_up`
counters grow: that is the test for any future latch experiment
(MODULE_EN without DB, an address register the HAL uses).

**Diagnostics** in `/sys/kernel/debug/mt6785-camsv-status`: mode,
INT_EN (and its write-clear bit), TG_FRMSIZE (px x lines, the old
label had them swapped), FBC_CTL1/CTL2, IMGO_BASE, and the IRQ path
counters since STREAMON: irqs, pass1_don, arms, frames, torn,
missed, gave_up, no_buffer, errors, storms, last INT_STATUS, FBC_CTL2
at the last PASS1_DON (and how often its [31:24] changed), and a
count per INT_STATUS bit.  It no longer reads INT_STATUS itself: in
read-clear mode that read would steal events from the handler.

## 0g. Seventh-boot postmortem (2026-11-17, one frame per stream)

Storm gone (VS, SOF and PASS1_DON once per frame, read-to-clear works
with bit 31 clear; the OV8856 640x480 mode runs at ~120 fps).  But one
buffer only, then a timeout.  Status after ~90 s: pass1_don 10762,
frames 1, missed 10761, gave_up 2690, FBC_CTL2 0x0a000001 after stop
and 0x09000001 at the last PASS1_DON, [31:24] changed on every
PASS1_DON.

**Not a cache problem**: the bounce buffer's marker areas are cleaned
(`dma_sync_single_range_for_device`) after the CPU writes them and
invalidated (`..._for_cpu`) before they are read, and the whole buffer
is invalidated before the copy (arm64: clean / invalidate to PoC).
The first frame passed through that same path.

**The FBC never released its buffer.**  In the ISP4/5 FBC layout
FBC_CTL2 is FBC_CNT[6:0] (buffers filled and not released), RCNT,
WCNT, and DROP_CNT[31:24].  The drop condition is FBC_CNT == FBC_NUM.
FBC_CTL2 = 0x..000001 with [31:24] +1 per frame reads as: one buffer
filled, never released, every later frame dropped.  The begonia runs
fit too (0xf4000001: 244 drops; 0x60000000 with FBC off).  So the
"RCNT_INC" write the experiments used (CTL1 0x8000 then 0x8001) is
most likely FBC_NUM = 1, not a release: it gives one frame from a
freshly reset FBC and nothing after.  Consequences:
- every stream since t8c wrote exactly ONE frame.  "Only buffer 0 has
  data" came from that, not from IMGO_BASE_ADDR.  Whether BASE_ADDR
  latches per frame is still untested (`rotate=1`, once frames flow);
- `ov-cap.py --frames N` never got more than its first frame either
  (one buffer, so it could not tell);
- FBC_CTL2[31:24] is a drop counter, not a frame counter.  Accepting a
  frame because it advanced would accept dropped frames, so the
  markers stay the deciding test.

**Fix attempted** (superseded by 0h: none of these released; the
`rearm` parameter is gone): a release before each arm, chosen by the `rearm` module
parameter (read at STREAMON, so it can be swept in one boot):
- 0 `toggle` (default): CTL1 = 0 (FBC off), then 0x8000, 0x8001.  This
  re-creates the fresh-FBC state that gave the first frame, in
  vertical blanking;
- 1 `pulse`: 0x8000, 0x8001 only (the t8g behaviour, for comparison);
- 2 `dmareset`: IMGO reset (SW_CTL 1, wait for 3, 0), window
  re-programmed, then as 0.
The status file shows the method and `FBC_CTL2 ... after last arm`:
a low byte back at 0 after the arm means the release worked.

Smaller changes: the second marker moved from the last 16 bytes to the
start of the LAST LINE, which tolerates a DMA that stops a few bytes
early.  A frame with the first line written but not the last one now
counts as `short` (re-armed, not delivered).  The capture script bounds
v4l2-ctl with `timeout` (frames + 10 s) so a stalled stream still
prints the status dumps.  The 380928-byte file of this run is 384000
minus 3072: the last partial 4 KiB stdio block v4l2-ctl had not
flushed when it was stopped.  The driver reports 384000 bytes.

## 0h. Eighth boot (2026-11-17): the FBC low field is not a release

(The "frame count" reading below is superseded by 0i; the zero-copy
scheme and the delivery rule stay.)

The `rearm` sweep: none of the three methods released (frames 1,
missed ~3600, "after last arm" FBC_CTL2 0x..000001 every time).  The
supervisor then poked FBC_IMGO_CTL1 through /dev/mem while streaming:
- 0x8001 (the driver's value): CTL2 low byte stuck at 1, [31:24] +1
  per frame (drops, ~120/s).  Poking 0x8000 then 0x8001, 0x8101 or
  0x18001 changes nothing; 0x418001 sets CTL2[23:16] to 2, still
  dropping;
- **0x8002**: the drop counter [31:24] FREEZES, and CTL2[7:0] and
  [23:16] count at the frame rate ([7:0] one ahead).  0x8003 and
  0x8004 behave the same.  Meanwhile the driver's marker test passed
  real frames (delivered went from 1 to 229);
- +0x118/+0x11c read 0 throughout; IMGO_BASE stayed at the address
  programmed at stream start; +0x400 = 1.

**Reading**: the low field of FBC_IMGO_CTL1 is a frame count, not a
release strobe ("RCNT_INC" in the begonia notes, T2, T3 and T4 is
wrong).  With 1 the DMA writes one frame per stream and drops the
rest.  With 2 or more it writes every frame, with no software release
at all.  CTL2[7:0] counts the frames written, [31:24] the frames
dropped.  Sections 2.2 and 6 below are corrected accordingly.

**Capture path now** (`mt6785-camsv.c`):
- the FBC is started once, at STREAMON, with `FBC_EN | fbc_num`
  (module parameter `fbc_num`, default 2, range 1-63, read at
  STREAMON); no per-frame re-arm;
- **rotate=1, the default (zero copy)**: at each PASS1_DON the hard
  interrupt first programs IMGO_BASE_ADDR with the next queued vb2
  buffer, so the next frame lands in it.  We are in vertical blanking
  (~0.3 ms at 120 fps) and the interrupt is serviced in microseconds;
  MODULE_EN keeps DB on.  With no buffer queued it parks the DMA on a
  driver-owned scratch buffer, because a free-running DMA must never
  write into a buffer userspace holds.  It then judges the buffer that
  was programmed for the frame that ended;
- **delivery rule**: a buffer is delivered if both markers
  (first-line and last-line start) written when it was programmed are
  overwritten.  Buffers without a kernel mapping (imported dmabuf)
  are delivered if CTL2[7:0] advanced.  Otherwise the buffer is put
  back at the queue head, never handed out, and counted: `missed`
  (the FBC wrote a frame but not into this buffer, i.e. the address
  did not take effect for that frame), `torn`, `short`.  A frame the
  counter did not see but the markers did is delivered and counted
  as `disagree`.  The markers stay because CTL2[7:0] only says "a frame
  was written", not where: they are the per-address proof that makes
  the zero-copy path checkable;
- **rotate=0 (bounce, fallback)**: the DMA always writes the scratch
  buffer.  At PASS1_DON the hard interrupt drops the frame count to 1
  (the FBC then holds after the frame in progress) and wakes the
  thread.  The thread checks the markers, copies into the next
  buffer, checks that CTL2[7:0] did not move during the copy
  (`copy_races` otherwise), re-marks, and sets the count back to
  `fbc_num`.  At most every other frame;
- **status file**: mode, FBC num, CTL2 split into written / [23:16] /
  dropped, IMGO_BASE read back next to the last address programmed
  and the scratch address, then pass1_don, hw_written (CTL2[7:0]
  advances), hw_idle, hw_multi, drops, delivered, missed, torn,
  short, disagree, parked, recycled, copy_races, errors, the INT_STATUS
  bit counts.

What a good zero-copy run looks like: delivered ≈ hw_written ≈
pass1_don (minus parked frames), missed/torn/short ≈ 0 apart from the
first frame (the TG may start mid-frame), drops not increasing.
`missed` ≈ hw_written instead means the address takes effect a frame
late (or never). Then use `rotate=0` and look at the MODULE_EN DB
bit next.

## 0i. Ninth boot (2026-11-17): the FBC compares a written count

Round 4 with `FBC_EN | 2` written once: exactly 2 frames written, then
every frame dropped (pass1_don 3601, hw_written 2, drops 3599,
delivered 2, recycled 3599).  The supervisor's /dev/mem pokes on CTL1
while the driver streamed without rewriting it (CTL2 as drops / [23:16]
/ [7:0]):
- NUM=2 with [7:0] = 2: stuck, drops rising.  NUM=0: stuck.  NUM=1
  while [7:0] = 2: flows (07, 2c, 33...), drops frozen.  NUM=2 at
  0x33: flows.  NUM=0 at 0x65: one more frame (0x66), then stuck;
- NUM=1 at 0x6c: flows up to 0x7f, wraps to 0, sticks at 1;
  NUM=3: counts to 3 and sticks.  NUM=0x3f at 0x40: flows, wraps,
  sticks at 0x3f;
- IMGO_BASE read back different buffer addresses over time: the
  per-frame address programming of 0h IS latched.

**Semantics** (supersedes 0g and 0h):
- CTL2[6:0] counts the frames written: 7 bits, wraps through 0, never
  decremented;
- CTL2[31:24] counts the frames dropped;
- the 6-bit low field of CTL1 is a compare value: the DMA stops when
  the written count EQUALS it, and always when it is 0;
- any other value lets frames flow, and a frame in progress when the
  value becomes 0 is completed.

No release mechanism was found, and none is needed.

**Driver**: the compare value is kept ahead of the count.  At STREAMON
(after the CAMSV reset) and in every PASS1_DON hard interrupt, after
IMGO_BASE_ADDR, the driver writes `FBC_EN | NUM` with
`NUM = (count + fbc_margin) & 0x3f`, or 1 if that is 0.  That value is
never 0 and never equal to the count, and a count of 64-127 can never
match the 6-bit field.  `fbc_margin` is a module parameter, 2-32,
default 8, read at STREAMON; the DMA would only stall if that many
frames went by without a PASS1_DON being serviced.  Only the low field
changes; FBC_EN stays set.  The bounce path holds the DMA with NUM = 0
while it copies, then writes the leading value again.  `fbc_num` is
gone.

Status file additions: FBC_CTL1 with its compare value, CTL2 with the
written count, a `STOPPED` flag when FBC_EN is set and the compare
value is 0 or equal to the count, and `stalls`: frame ends that found
the count equal to the compare value (it should stay 0).

## 1. Architecture

Two platform drivers in `drivers/media/platform/mediatek/mt6785-cam/`,
Kconfig `VIDEO_MEDIATEK_MT6785_CAM`, one module each:

| Module | Device | Role |
|---|---|---|
| `mt6785-seninf.ko` | `seninf@1a040000` | CSI-2 receiver subdev. Registers the media device and the v4l2_device, runs the async notifier that binds the sensor, performs the validated PHY/CSI2/MUX/TOP_MUX sequence on s_stream. |
| `mt6785-camsv.ko` | `camsv@1a050000` | CAMSV0 raw capture. Registers itself as an async subdev; when the SENINF notifier binds it, its `.registered` internal op creates the vb2 video node. The frame-done IRQ completes buffers. |

Media graph (entity names as registered; the video entity is
"mtk-mt6785-camsv video", distinct from the subdev):

```
ov8856 2-0036 (pad 0) ──[ENABLED]──┐             [sensor subdevs, one
s5k4h7 4-002d (pad 0) ──[0]───────┤              per CSI port; exactly
                                   v              one link enabled]
        mtk-mt6785-seninf (pads 0..2 sink = CSI ports 0..2, pad 3 source)
              └─> mtk-mt6785-camsv (pad 0 sink, pad 1 source)
                    └─> "mtk-mt6785-camsv video" /dev/videoN (MEDIA_ENT_F_IO_V4L)
```

- The SENINF owns the `media_device` (`mtk-mt6785-cam`) and the
  `v4l2_device`; its notifier scans ports 0..2 of its own DT node for
  remote endpoints (sensors) and also waits for the CAMSV subdev
  (the port@3 -> camsv0 endpoint pair in `mt6785.dtsi`).  The entity
  implements `.get_fwnode_pad = v4l2_subdev_get_fwnode_pad_1_to_1`
  so the DT port number maps to the same-numbered sink pad.
- Sensor binding: `v4l2_async_nf_add_fwnode()` on the remote endpoint;
  lane count (`data-lanes`) is parsed from the sensor-side endpoint
  (where the property lives) at notifier-setup time.  On bind, the
  sensor's source pad is resolved from that endpoint
  (`media_entity_get_fwnode_pad`) and the link is created with
  `media_create_pad_link`, enabled for port 1 only (0e).
- CAMSV0 is hardwired to SENINF mux 2 / cam_mux 2 on this SoC (vendor
  HAL `convertTgEnum2CamMux = tg - 14`), so the SENINF source pad always
  routes through TOP_MUX[2] and CAM_MUX_EN bit 2; the media graph models
  that as a single source pad.

Both drivers use the plain `.s_stream()` subdev API (no
V4L2_SUBDEV_FL_STREAMS): the pipeline is a rigid single-stream chain and
the upstream ov8856 driver still implements s_stream.

## 2. Register sequences and their provenance

Every hardware write in both drivers mirrors `tools/camera/ov-cap.py`
(the validated sequence) in the same order. Line numbers refer to
`ov-cap.py` as of commit "camera: first frames from the OV8856 through
SENINF and CAMSV" (dd87283).

Then the sensor is started through its own subdev s_stream (ov-cap.py
applies the OV8856 tables over I2C; that is the mainline ov8856
driver's job now).

Stream-off reverses: mux disabled and reset, CSI2_EN = 0, CSI2_CTRL/SENINF
off, ANA LPF/CORE cleared, port back to CPHY mode (0x2) — reverse of
ov-cap.py's setup so a re-start re-runs the whole sequence.

**HS-settle**: no formula exists in the reachable sources (the ISP7
phy_2_0 reference carries it as per-SoC platform data
`core->dphy_settle_delay_dt`; the vendor HAL sets it from unexposed
tables).  What is known: 15 was validated at 360 MHz link frequency
(720 Mbps/lane) on this tablet; the begonia settle sweep found a wide
working window; the D-PHY spec window is [85ns+6UI, 145ns+10UI] with
UI = 1/(2*link_freq), dominated by its fixed part (its centre moves
by less than 5 % between 720 and 1400 Mbps/lane).  The driver
therefore writes 15 for every mode; the `hs_settle` module parameter
(default 15, writable at runtime in
`/sys/module/mt6785_seninf/parameters/hs_settle`, read at each
stream-on) is the knob for a sweep if the 645 MHz modes show noise.
The status dump prints the link frequency and settle of each port.

**Multiple sensors**: `struct mt6785_seninf_port` per CSI port holds
the bound subdev, its source pad and lane count.  Every bound sensor
is linked to its port's sink pad; the links are not immutable and
exactly one is enabled (`link_setup` switches the selection itself
when another link is enabled and not streaming, and refuses any change
while streaming — see section 8.2).  `s_stream` streams the port whose
link is enabled (`seninf_enabled_port()`), which is also the only
sensor link `media_pipeline_start()` walks and validates.  The routing
(TOP mux nibble) is reprogrammed per stream-on for that port's SENINF
instance.

### 2.2 CAMSV0 start/stop (mt6785-camsv.c)

Split into `camsv_hw_config()` and `camsv_hw_enable()` to reproduce the
**`--stream-first` order** that the experiments validated on this
tablet (ov-cap.py `--stream-first`, and begonia NOTES.md "Where we
stopped": arming the TG before the sensor streams leaves IMGO in
IMGO_ERR):

1. `camsv_hw_config()` = ov-cap.py `setup_camsv0()` with
   `--layout le10` (lines 379-407): pre-stop
   0x230/0x234/0x510=0x40000000/0x110, SW_CTL reset 4->0->1(wait
   ==3)->0, GRAB_PXL = W<<16, GRAB_LIN = L<<16, IMGO
   BASE/XSIZE=BPL-1/YSIZE=L-1/STRIDE=BPL — no bit 24! —/CON2/CON3 =
   0x20002, **FMT_SEL 0x102, PAK 1** (measured complete-frame layout;
   the begonia 0x101/2 writes 12-bit containers and truncates lines,
   see section 3), FBC 0x8000 | compare value fbc_margin ahead of the written count (0i), CLK_EN 0x8005, MODULE_EN 0x40000015,
   INT_EN 0x001304b1 (the vendor HAL value; NOT 0xffffffff, see 0f),
   0x400 = 1), with the two final writes
   (VF_CON = 1, SEN_MODE = 0x10001) withheld.  BPL = width * 10 / 8.
2. SENINF s_stream(1) (sequence above, ends with the sensor streaming).
3. `camsv_hw_enable()` = the withheld VF_CON = 1 and
   SEN_MODE = 0x10001.

Frame completion (0h): the hard interrupt reads and clears
INT_STATUS and counts it.  At PASS1_DON (bit 10) it reads FBC_CTL2
(written-frame counter [7:0], drop counter [31:24]).  In zero-copy
mode (default) it then programs IMGO_BASE_ADDR for the next frame
(next queued vb2 buffer, or the scratch buffer) and delivers or
recycles the buffer programmed for the frame that ended, by its
markers, and writes the FBC compare value fbc_margin frames ahead of
the written count (0i).  In bounce mode it holds the FBC (compare value
0) and wakes the thread, which copies and writes the leading value
again.  Each delivered buffer gets the PASS1_DON index as sequence and
a monotonic timestamp.  FBC bits 16/22 stay clear (they stall the DMA, begonia notes).
`IMGO_ERR` (bit 16) is reported with a rate-limited error pointing at
the LARB bypass; TG_ERR (bit 4) is debug-only (the experiments see it
on good captures too).  Note the OV8856 at 640x480 delivers 481 lines
per TG_FRMSIZE; the DMA window (YSIZE/GRAB_LIN = height) is set to
the requested 480 and the frame completes — do not size the window
for 481.

Stop: sensor off through the pipeline, TG off, DMA off, FBC off, all
queued buffers returned with VB2_BUF_STATE_ERROR, LARB MMU re-enabled.

### 2.3 IOMMU: contiguous buffers + LARB bypass (deliberately simple)

vb2 `vb2_dma_contig` with a 32-bit DMA mask gives physically contiguous
CMA buffers; `camsv_larb_bypass()` clears MMU_EN (bit 0 of
`SMI_LARB_NONSEC_CON`, 0x380+4*port) on all 31 larb6 ports (mapped
through the `mediatek,larb6` phandle, its APB clock is in the clock
list) and all 5 larb7 ports (window from the camsv node's second reg
tuple — larb7 has no DT node in this tree yet), exactly like
`tools/camera/larb-bypass.py`. This is done in the kernel while
streaming and undone on stop, with a clear FIXME: proper IOMMU support
(mapping the camera LARB ports into the M4U) is future work.

## 3. Formats

The sensor emits MEDIA_BUS_FMT_S*10_1X10-family codes.  With the
measured IMGO configuration (CAMSV `FMT_SEL (0x514) = 0x102`, `PAK
(0x54c) = 1`, line sized for 10 bits: bytes per line = width * 10 / 8,
docs/hardware/CAMERA.md "Frame layout and first photo"), each line is
a **continuous little-endian 10-bit bit stream**: pixel k occupies bits
10k..10k+9 of the line read as a little-endian integer.

**Format mismatch (deliberate, documented):** no V4L2 fourcc documents
this exact bit layout.  Checked in this tree:
`V4L2_PIX_FMT_S*10P` (pixfmt-srggb10p.rst) is the MIPI RAW10 layout
(4 pixels per 5 bytes, MSB bytes first + one LSB byte) — same
bytes-per-line, different bit order.  `V4L2_PIX_FMT_IPU3_S*10`
packs 25 pixels per 32 bytes with padding; `V4L2_PIX_FMT_RAW_CRU10`
packs into 64-bit units.  None matches.  The driver therefore exposes
the closest packed 10-bit Bayer fourcc matching the sensor bus code
(`MEDIA_BUS_FMT_SBGGR10_1X10` -> `V4L2_PIX_FMT_SBGGR10P`, etc.),
single-plane, BPL = width * 10 / 8, sizeimage = BPL * height, and
userspace MUST decode with `tools/camera/raw2rgb.py --layout le10`
(or a decoder written for this bitstream) — a generic S*10P decoder
produces garbage.  `tools/camera/v4l2-capture.sh` does exactly that.
When this ever goes to libcamera, the soft ISP debayer needs an
le10 unpacker (or CAMSV must be switched to a layout a standard
fourcc describes, which the hardware may not offer).

The old begonia values (`FMT_SEL = 0x101`, `PAK = 2`) are NOT used:
on this board they make IMGO write 12-bit containers (2 px per 3
bytes, sample << 2) and truncate each line to 2/3 of the pixels
(533 of 640).  `ov-cap.py --layout p12` keeps them for reference.

## 4. Device tree

SoC (`mt6785.dtsi`): `seninf@1a040000` (SENINF 0x6000 + MIPI RX ANA
0x11c80000/0xc000, CAM power domain, camsys+top-seninf0..2+APMIXED
mipic0/1 clocks, ports 0..2 CSI sinks + port 3 source) and
`camsv@1a050000` (CAMSV0 + larb7 windows, GIC_SPI 279, CAM domain,
camsys gates incl. LARB6/7 + the same muxes, `mediatek,larb6`), both
`status = "disabled"` by default.

Board (`mt6785-lenovo-yt-j706f.dts`):

- `&seninf`/`&camsv0` enabled; seninf port@1 endpoint wired to the
  sensor (CSI port 1 = SENINF2 is where the OV8856 packets arrive,
  CAMERA.md).
- Fixed regulators for the GPIO-switched rails: `vcama` (GPIO195,
  2.8 V), `vcamd` (GPIO50, 1.1 V), `vcamaf` (GPIO197, 2.8 V), all
  `enable-active-high`.  **No `pinctrl-0` on them** (first-boot
  lesson): a pinctrl state is exclusive per device, and all three
  shared `cam_gpio_pins` (5 pins each), so the second regulator failed
  its probe with -EBUSY and `i2c 2-0036` stayed on
  `deferred probe pending: supplier regulator-vcamd not ready`.
  The regulator-fixed driver muxes its own `gpio` pin through
  gpiod without a pinctrl state; the pins come up as GPIOs on
  demand.  The `camera-probe` (M0) node is now `status = "disabled"`
  too — its driver does `devm_gpiod_get` on the same GPIOs
  (195/50/197/119) and would collide with the regulators and the
  sensor reset.
- `ov8856@36` on `&i2c2`: `ovti,ov8856`, MCLK `CLK_TOP_CAMTG2` at
  24 MHz (`assigned-clock-parents = CLK_TOP_UNIVPLL_192M_D8`, pin
  CMMCLK1 = GPIO117 through the existing `cam0_mclk_on` pinctrl),
  `reset-gpios = GPIO119 GPIO_ACTIVE_LOW` (high = run per CAMERA.md;
  the mainline driver asserts reset with value 1 = physical low),
  supplies dovdd = MT6359 vcamio / avdd = vcama / dvdd = vcamd,
  endpoint `data-lanes = <1 2>`, `link-frequencies` listing the
  union of the patched 24 MHz lane config (645 + 360 MHz) and the
  unpatched 19.2 MHz one (720 MHz; extra entries are allowed, each
  menu item must be present), remote-endpoint to seninf port@1.
- `s5k4h7@2d` on `&i2c4`: `samsung,s5k4h7` (T7 driver), MCLK
  `CLK_TOP_CAMTG3` at 24 MHz (pin CMMCLK2 = GPIO120 through
  `cam1_mclk_on`), `reset-gpios = GPIO124 GPIO_ACTIVE_LOW`, same
  vcama/vcamd rails (regulator reference counting — both sensors can
  hold them), 4 data lanes, 700 MHz link frequency, endpoint on
  seninf port 0 **as a guess**; the DT comment above the node says
  exactly which one line to change on each side to move it to port 2
  once the port search says so.
- The M2 experiment nodes (`seninf-tm@1a040000`, `camsv-tm@1a050000`)
  conflict with the new nodes over the same register windows, so they
  are kept in the DT but `status = "disabled"`; the modules remain
  buildable for a rollback boot with a DT that re-enables them.

## 6. What is NOT done

- **IOMMU**: LARB MMU bypass instead of mapping camera ports into the
  M4U (larb7 has no DT node; `mtk_iommu.c` larbid_remap lacks larb 7;
  the CAMSV port id on larb6/7 is unknown until probed port-by-port).
- **Second sensor (S5K4H7, cam1)**: DT node added, the seninf selects
  between the bound sensors by link (`-c s5k4h7` in the script), but
  its CSI port is a guess (0) until the port search on hardware; only
  CAMSV0 is driven, so the two sensors cannot capture simultaneously
  anyway.
- **Per-frame address latency**: zero copy relies on IMGO_BASE_ADDR,
  written in vertical blanking, taking effect for the very next frame
  (MODULE_EN DB on).  Checked per frame by the markers (`missed`); if
  it fails, `rotate=0` (copy) works regardless, and MODULE_EN without
  DB (0x15) is the next experiment.
- **FBC semantics**: only measured, not documented: CTL1 low field =
  compare value (the DMA stops when the written count CTL2[6:0]
  equals it, or when it is 0; 0i), CTL2[6:0] = written,
  [31:24] = dropped, [23:16] trails [7:0].  The vendor HAL's bits 16
  and 22 are still unexplained.
- **Other CSI ports / CAMSV1..5**: routing supports any of ports
  0..2 -> mux 2 -> CAMSV0, but only CAMSV0 exists.
- **Full-resolution modes**: the ov8856 24 MHz lane config
  (fb92c734a) covers 640x480, 1632x1224 and 3264x2448, all wired
  through the pipeline now.  Not yet validated on hardware at
  645 MHz link frequency: the settle scaling is an informed guess
  (section 2.1).  The DT keeps 720 MHz in `link-frequencies` as well
  so a tree without that commit still probes.
- **Suspend/resume**: system suspend is force-suspend of runtime PM;
  nothing reprograms the pipeline after resume.
- **libcamera simple pipeline**: not wired (`mtk-seninf` entry in
  simple.cpp has `swIspEnabled = false` upstream).
- **DT bindings documentation** for the two new compatibles is not
  written (out of scope for T8's file list).

   ```sh
   cat /sys/kernel/debug/mt6785-seninf-status
   cat /sys/kernel/debug/mt6785-camsv-status
   ```
   Expect for a good OV8856 run on port 1: `selected port 1`, the port
   line with `sensor ov8856 2-0036, link freq 360000000 Hz, settle 15`
   at 640x480 (645000000 at the larger modes), ANA cal `1/1`, CSI2
   PACKET_CNT non-zero, DPHY `clk/dat` FSMs at 0x01 idle after the
   stream (0x10 while streaming), MUX2/CAM_MUX2 sizes of the last
   frame (640x480-ish; CAM_MUX2 CHK_RES reads 0x01e00a00 on good
   runs too), CAMSV TG_FRMSIZE `640 px x 481 lines`, and the counters
   of step 2 ("released").

5. **S5K4H7 (cam1) and its CSI port**
   ```sh
   v4l2-ctl -d /dev/v4l-subdevN -l     # the s5k4h7 node: its controls
   sh tools/camera/v4l2-capture.sh -c s5k4h7 -n 5 -t
   cat /sys/kernel/debug/mt6785-seninf-status
   sh tools/camera/v4l2-capture.sh -c ov8856 -n 3 -t   # switch back
   ```
   The script disables the OV8856 link, enables the S5K4H7's, sets
   640x480 (code from the sensor, SGRBG10 unless flipped -> pgAA, grbg)
   and streams.  The S5K4H7 is wired to seninf port 0 in the DT, a
   guess: if the capture times out and the dump shows port 0 with
   PACKET_CNT 0 and the DPHY FSMs idle while the sensor was streaming,
   the sensor is on port 2 instead — move the endpoint (one line each
   side, see the i2c4 comment in the board DTS), rebuild, retest.  A
   port with packets but a wrong lane count shows CSI2 IRQ_STATUS
   errors in the same dump (the DT says 4 lanes).

6. **If something fails**
   - **No /dev/media0, seninf probe error**: the dmesg line before the
     error names the port and step (`no source pad for the port N
     endpoint`, `failed to link ...`).
   - **`VIDIOC_STREAMON: Link has been severed` + `no SENINF
     connected`**: the seninf->camsv link is missing — check
     `media-ctl -p` and the `bound on port 3` notifier message.
     `no bound sensor with an enabled link`: no sensor link is enabled
     (step 1 left both off) — run the script with `-c`.
   - **`format mismatch` in dmesg at STREAMON** (EPIPE): names both
     pads and formats; the script sets every pad, so a mismatch means
     a pad set by hand afterwards.
   - **dqbuf timeout, no frames**: read the debugfs dumps (step 4):
     ANA cal bits clear -> APMIXED mipic gates; DPHY FSM idle while
     the sensor streams -> wrong CSI port or PHY sequence; CSI2
     PACKET_CNT advancing but MUX SIZE zero -> routing (TOP mux);
     camsv `pass1_don` 0 -> no frame end reaches CAMSV (b10 count 0);
     `pass1_don` growing but `frames` 0 with `missed`/`gave_up`
     growing -> the DMA writes nowhere near the bounce buffer: report
     the camsv dump.
   - **`interrupt storm ... does not clear` in dmesg**: INT_STATUS is
     cleared neither by reading nor by writing; report the
     `last INT_STATUS` and the bit counts.
   - **`IMGO DMA error` in dmesg, buffer stale**: LARB bypass not
     effective — `mediatek,larb6` phandle, the larb7 reg tuple, the
     `cam-larb6/7` clocks (`clk_summary`).
   - **Image decodes to garbage stripes**: wrong layout — only
     `--layout le10` matches this driver; `raw2rgb.py --auto` can
     detect what a file holds.
   - **A few frames, then a timeout, `STOPPED` in the status file**:
     the FBC compare value caught up with the written count (`stalls`
     > 0); report FBC_CTL1/CTL2.  Raising `fbc_margin` helps only if
     frame ends were missed.
   - **Timeout with `missed` growing**: the per-frame address does not
     take effect; use `rotate=0` (step 2).
   - **Bars tinted/shifted**: wrong Bayer order for the mode —
     `raw2rgb.py --auto` prints channel stats.

7. **Regression vs the experiment path**: to reproduce the M2 capture
   independently, boot a DT with the `-tm` nodes re-enabled and run
   `tools/camera/ov-cap.py --csi-port 1 --seninf 2 --layout le10` as
   documented in T2-SENINF-CAMSV.md; the register state it leaves
   behind can be compared with the driver's through the debugfs dumps
   plus `devmem2` on the same window.

## 8. Standard unpacked layout as the driver's format (2026-11-17, T15)

The layout sweep (T14 tools, CAMERA.md "Standard 16-bit layout and
autofocus actuator") found that FMT_SEL 0x102 with PAK 5 and two bytes
per pixel writes each 10-bit sample in a little-endian 16-bit word,
value in the low bits — the standard V4L2 unpacked Bayer layout. This
change makes it the driver's format, so libcamera's software ISP (and
any generic decoder) reads the frames natively.

### 8.1 Format negotiation changes (mt6785-camsv.c)

- The format table maps the four 10-bit Bayer media bus codes to the
  **unpacked** fourccs (`V4L2_PIX_FMT_SBGGR10` 'BG10', `SGBRG10`
  'GB10', `SGRBG10` 'BA10', `SRGGB10` 'RG10') — the packed `S*10P`
  entries and the PIXEL FORMAT MISMATCH paragraph are gone.
- Default and only advertised layout: FMT_SEL 0x102, PAK 5, BPL =
  width * 2, sizeimage = BPL * height. Colorspace raw
  (`V4L2_COLORSPACE_RAW`, `V4L2_XFER_FUNC_NONE`) on the video node
  and the subdev pad defaults.
- `ENUM_FMT` honours the `mbus_code` filter the V4L2 core passes
  through because of `V4L2_CAP_IO_MC` (the latent §5-3 gap: it
  returned every fourcc regardless of the code).
- `ENUM_FRAMESIZES` returns **discrete** sizes taken from the active
  sensor's `enum_frame_size` (through the enabled seninf link, the
  seninf now implements `enum_frame_size` on its pads and forwards to
  the bound sensor; the video node walks pad 3 -> the selected sink).
  With no reachable sensor it keeps the continuous 16..4624 x 16..4032
  range (geometry is pass-through, so a size set by hand still
  streams).
- The `fmt_sel` / `pak` / `bytes_per_px_x8` module parameters remain
  for experiments, defaulting to the standard values (0/5/16). Any
  override — including `bytes_per_px_x8=0`, which falls back to a
  10-bit line (the old le10 stride) — logs a `dev_warn` at STREAMON,
  and the debugfs "layout" line gains an `[OVERRIDDEN]` tag.
  `bytes_per_px_x8=16` (and the equivalent 0) keep the BPL at
  width * 2, so a sweep back to le10 needs `bytes_per_px_x8=10`.
- Registration message now says "unpacked 10-bit Bayer, 2 bytes/px".

### 8.2 Selector and sensor-side changes

- `seninf_link_setup()`: enabling a second sensor link while not
  streaming now SWITCHES the selection (the previously enabled link is
  disabled inside link_setup, before the core sets the new flag)
  instead of returning -EBUSY. One `media-ctl -l ... [1]` selects a
  sensor; libcamera's simple pipeline, which enables links itself,
  works without a disable-first dance. Switching while streaming still
  returns -EBUSY. The capture script keeps its explicit disable loop
  (harmless, and it covers older drivers).
- Board DT: `orientation`/`rotation` fwnode properties on both sensor
  nodes (cam0 OV8856 back/90, cam1 S5K4H7 front-assumed/270), marked
  provisional; the drivers already parse them into
  `V4L2_CID_CAMERA_ORIENTATION`/`_SENSOR_ROTATION`.

### 8.3 Script fixes

- `tools/camera/v4l2-capture.sh` uses the unpacked fourccs
  (BG10/GB10/BA10/RG10), BPL = width * 2 and decodes with
  `raw2rgb.py --layout u16` by default.
- `tools/camera/layout-sweep.sh` had two defects that made every
  candidate end with "no output file (capture never started?)" on the
  tablet while the same capture by hand worked: (a) the pipeline exit
  status of `if ! capture | grep -E ...` is GREP's, so "capture
  failed" printed exactly when the capture succeeded and printed its
  `==` lines, and printed nothing when the capture died; (b) the grep
  also swallowed every line not starting with `==|error|warning` —
  including the `media-ctl`/`v4l2-ctl` error output that precedes a
  `set -e` abort inside v4l2-capture.sh, so a capture that died before
  creating the file (or left a stale one from an earlier candidate)
  looked clean and empty. The sweep now removes any stale output file,
  runs the capture to a per-candidate log (`/tmp/sweep-<...>.log`) and
  tests the capture's own exit status; the interesting lines are
  echoed from the log, which is kept for the post-mortem.
