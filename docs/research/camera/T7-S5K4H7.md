# Task T7: V4L2 Sensor Driver for the Samsung S5K4H7 (cam1)

Research and implementation notes for the S5K4H7 driver written in
`src/mt6785-mainline/drivers/media/i2c/s5k4h7.c` (new, plus Kconfig,
Makefile, DT binding `samsung,s5k4h7.yaml` and `CONFIG_VIDEO_S5K4H7=m`
in `kernel/configs/yoga11.config`). The sensor is the tablet's second
camera: **cam1**, I2C address **0x2d** on i2c4 (0x11011000),
**chip ID 0x487b** at registers 0x0000/0x0001, 24 MHz master clock from
`CLK_TOP_CAMTG3` (GPIO120/CMMCLK2), reset GPIO124 (high = run), supplies
vcamio = MT6359 `vcamio` 1.8 V and the shared GPIO-switched vcama
(GPIO195) / vcamd (GPIO50) rails — see
[docs/hardware/CAMERA.md](../../hardware/CAMERA.md).

---

## 1. Sources found

### Upstream / mainline status

- **No mainline driver exists** for the S5K4H7 in Linux 7.1 (checked
  `drivers/media/i2c/` of this tree: `s5k3m5`, `s5k5baf`, `s5k6a3`,
  `s5kjn1` only) and none is queued in linux-next.
- **lore.kernel.org linux-media**: web search finds references to an
  old Qualcomm-downstream `s5k4h7` V4L2 subdev driver (2017 era,
  msm/camera_v2 sensor libs) and mailing-list discussions, but no
  merged or actively maintained mainline-style patch series. The
  existing upstream Samsung drivers (`s5k5baf`, `s5k6a3`, `s5k4ecgx`)
  predate this sensor.
- **postmarketOS / device trees**: no `samsung,s5k4h7` binding anywhere
  in device trees I could reach; downstream phones that carry this
  sensor (Xiaomi Merlin/mt6768, several Realme/Oppo mt6853/6833, Nokia
  mt6771, Lenovo Tab mt8792) all use the MediaTek vendor `imgsensor`
  framework instead.

So the driver is written from scratch, modelled on in-tree drivers
(see below), with register tables transcribed from the MediaTek GPL
vendor drivers.

## 2. What the tables are and where each one comes from

All tables in the driver are verbatim transcriptions of the vendor
register sequences (streaming-off prefix kept, vendor runtime state
writes dropped). Each table cites its source in a comment.

| Driver table | Vendor source | Content |
|---|---|---|
| `s5k4h7_init_regs` | Lenovo `addr_data_pair_init[]` (identical to the `sensor_init()` function bodies in Merlin/Nokia/Realme) | Global analog init: bias, PLL pre-config, LSC masks; ends with 0x30cf = 0 (digital gain off) |
| `s5k4h7_3264x2448_30fps_regs` | Lenovo `addr_data_pair_capture[]` | Full 8MP mode: PLL 0x0305..0x030F, MIPI 0x0820/0x0821 = 700 Mbps, RAW10 0x0112/0x0113, 4 lanes 0x0114 = 3, crop 0x0008..0x0cc7 x 0x0008..0x0997, output 3264x2448, VTS 0x09E2 = 2530, HTS 0x0E68 = 3688, exposure default 0x0DD8 = 3544 lines |
| `s5k4h7_3264x1836_30fps_regs` | Lenovo `addr_data_pair_normal_video[]` | Same PLL/timings, vertical crop 0x013a..0x0865, output 3264x1836 (16:9) |
| `s5k4h7_1632x1224_30fps_regs` | Lenovo `addr_data_pair_preview[]` | 2x2 binning (0x0387 = 0x03, 0x0900/0x0901 = 0x01/0x22), full crop, output 1632x1224 |
| `s5k4h7_640x480_120fps_regs` | Merlin `hs_video_setting()` (S5K4H7YX) | 4x4 binning (0x0387 = 0x07, 0x0900/0x0901 = 0x01/0x44), crop 0x0168..0x0b67 x 0x0110..0x088f, output 640x480, VTS 0x0278 = 632 → 280 MHz / (3688 × 632) ≈ 120 fps |

### Timing and link-frequency numbers

- Pixel clock (pclk) = **280 MHz** in every 0x487B vendor mode
  (Lenovo `pclk = 280000000`, HTS 3688 × VTS 2530 = 9 330 640 ≈ 30 fps).
- MIPI: 4 lanes, RAW10, 700 Mbps/lane (Lenovo `mipi_pixel_rate` 280 MHz
  and Merlin's `$MIPI[DataRate:700]`) →
  **link frequency 700 MHz**, pixel rate reported to V4L2 =
  700 MHz × 2 (DDR) × 4 lanes / 10 bits = **560 MHz**…
  the driver instead reports `S5K4H7_PIXEL_RATE = link_freq × 2 ×
  lanes / bits = 700e6 × 2 × 4 / 10 = 560 MHz`. Note this is the CSI
  *symbol* rate; the vendor's "mipi_pixel_rate" of 280 MHz equals
  700e6 × 4 / 10. The V4L2 `PIXEL_RATE` control here uses the
  same formula as in-tree drivers (s5kjn1: `freq * 2 * lanes / 10`),
  which is what receivers expect.
- MCLK: **24 MHz** in all sources (`mclk = 24`, 0x0136 = 0x18 = 24
  decimal). The driver rejects any other rate at probe.

### Controls (all register semantics confirmed by at least two vendor trees)

- **Exposure**: 0x0202/0x0203, coarse integration time in lines, 16-bit.
  Default 0x0DD8 = 3544 lines (~11.3 ms at 30 fps), margin 6 lines
  (Nokia `margin = 6`; Merlin uses 4 — driver uses 6).
- **Analogue gain**: 0x0204/0x0205, **linear, gain = code / 32** —
  the Lenovo `s5k4h7_ana_gain_table.h` enumerates 1024..16384
  (= gain × 1024, i.e. 1x..16x) in steps of 32 with
  `get_gain2reg(gain) = gain * 32 / BASEGAIN` (BASEGAIN = 1024),
  so code = realgain × 32: 1x → 32 (0x20), 4x → 128 (0x80, the vendor
  default `ana_gain_def = BASEGAIN * 4`), 16x → 512 (0x200). The driver
  exposes V4L2 range 32..512 step 1, default 128 — i.e. milli-gain
  convention is avoided and userspace sets code/32 as an integer
  multiplier × 32.
- **VBLANK**: via frame length 0x0340/0x0341 (VTS; register holds
  `height + vblank`), max 0xFFFF (Nokia `max_frame_length`).
- **HBLANK**: via line length 0x0342/0x0343 (HTS 3688, fixed per mode,
  read-only control updated on format change).
- **Flips**: 0x0101 bit0/bit1 (Realme `set_mirror_flip`; bit0 = V flip,
  bit1 = H mirror in its IMAGE_V_MIRROR = 0x01 / IMAGE_H_MIRROR = 0x02
  switch). The driver writes (vflip ? BIT(1) : 0) | (hflip ? BIT(0) : 0)
  following the s5kjn1 convention and swaps the reported Bayer code
  (SGRBG10 default, `SENSOR_OUTPUT_FORMAT_RAW_Gr` in all vendor trees)
  across the four `MEDIA_BUS_FMT_*10_1X10` variants like s5kjn1 does.
- **Test pattern**: 0x0600 (16-bit): 0 = off, 1 = colour bars
  (Lenovo `subdrv_i2c_wr_u16(ctx, 0x0600, mode) /* 100% Color bar */`,
  Realme writes 1 + the 0x6028/0x0602..0x0608 solid-colour registers).
  The driver menu keeps only modes the vendor code actually exercises:
  Disabled, Color bars; "Solid color" and "PN9" entries follow the
  Samsung 0x0600 convention of s5kjn1 and are **untested** (values
  written are 2 and 3 — assumption, see §4).

### Power sequencing

Lenovo mt8792 `pw_seq[]`: MCLK → (driving current) → RST active →
DVDD → AVDD → DOVDD(1.8 V) → RST release. The driver's power_on:
assert reset, 10 ms, enable avdd+dvdd+dovdd bulk, enable MCLK, release
reset, 10 ms. Power off: assert reset, disable MCLK, disable supplies.
GPIO124 is **high = run** in the stock DT, i.e. active-low `reset-gpios`.

## 3. The driver

`drivers/media/i2c/s5k4h7.c`, ~900 lines:

- Modelled on **`drivers/media/i2c/og0ve1b.c`** (structure: CCI regmap,
  runtime PM, single-pad subdev, `enable_streams`/`disable_streams`,
  `v4l2_async_register_subdev_sensor`) with the multi-mode control
  update pattern of **`drivers/media/i2c/s5kjn1.c`** (mode-dependent
  hblank/vblank/exposure ranges on `set_fmt`, flip controls that swap
  the Bayer code, Samsung CCS-style register names).
- Verified against this tree: `devm_cci_regmap_init_i2c`,
  `cci_write/cci_read/cci_multi_reg_write`,
  `devm_v4l2_sensor_clk_get`, `v4l2_link_freq_to_bitmap`,
  `v4l2_subdev_s_stream_helper`, `v4l2_ctrl_new_fwnode_properties`
  all exist (grep). Compiles clean (`CC [M] drivers/media/i2c/s5k4h7.o`,
  no warnings) in the project kbuild container against defconfig +
  `CONFIG_VIDEO_S5K4H7=m` (isolated volume; full modpost not run —
  single-module build without a kernel image has no Module.symvers).
- Clock: `devm_v4l2_sensor_clk_get` + `clk_get_rate` == 24 MHz check
  (fails probe otherwise, like s5kjn1).
- Endpoint parsing: requires exactly 4 `data-lanes` and a
  `link-frequencies` entry of 700 MHz.
- Probe powers the sensor up, reads the ID, and leaves it runtime-
  suspended.

## 4. Assumptions and uncertainties

1. **Register meanings partially guessed**: the PLL (0x0301..0x030F,
   0x0820..0x0823), crop/binning (0x0344..0x034F, 0x0381..0x0387,
   0x0900/0x0901) and MIPI (0x0112..0x0114) blocks are transcribed
   verbatim; individual bit meanings are inferred from the CCS-style
   layout and cross-vendor consistency, not from a datasheet (no
   S5K4H7 datasheet is public). Comments name registers by best
   inference.
2. **Untested on hardware** — no tablet access in this task. The
   OV8856 bring-up showed sensors may need vendor-specific quirks
   (stream-off settle, PLL lock wait); the driver inserts a 10 ms
   delay before stream-on where the vendor drivers poll the frame
   counter (0x0005) instead.
3. **640x480 mode from the S5K4H7YX variant**: the Merlin hs_video
   table targets chip 0x487C, not 0x487B. PLL and MIPI registers are
   identical to the 0x487B tables, so it is expected to work; if the
   first frames from it are corrupt, drop the mode (one-line change in
   `s5k4h7_modes[]`).
4. **Test-pattern menu beyond "Color bars"** (Solid color = 2, PN9 = 3):
   pattern values follow the s5kjn1 0x0600 menu; the vendor code only
   ever writes 0/1. Treat 2/3 as unverified.
5. **PIXEL_RATE formula** uses `link × 2 × lanes / bits` (s5kjn1
   convention, 560 MHz). The vendor's own "mipi_pixel_rate" is
   280 MHz (`link × lanes / bits`). If the future SENINF/CAMSV
   receiver computes timing from PIXEL_RATE the way T2's test model
   did, this may need aligning to the vendor number.
6. **Exposure default** 0x0DD8 = 3544 lines comes from the mode tables
   (0x0200/0x0201). It exceeds VTS − margin (2524), so `set_fmt` clamps
   it via the control range; harmless but noted.
7. **Bayer order**: `SENSOR_OUTPUT_FORMAT_RAW_Gr` in all vendor trees →
   SGRBG10 assumed at orientation 0. Flip-related Bayer swapping
   mirrors s5kjn1 but is unverified on this sensor.

## 5. Ready-to-paste DT node (NOT added to the board DT)

For `mt6785-lenovo-yt-j706f.dts`, inside `&i2c4`. GPIO numbers and
rails per docs/hardware/CAMERA.md and the existing `camera_probe` node;
the fixed regulators and pinmux go at the top level / `&pio` like the
existing wifi and camera-probe nodes. The `remote-endpoint` waits for
the real SENINF driver (T2 test models use debugfs, no endpoint).

```dts
/* top level */
cam1_vcama: regulator-cam1-vcama {
	compatible = "regulator-fixed";
	regulator-name = "cam1_vcama";
	regulator-min-microvolt = <2800000>;
	regulator-max-microvolt = <2800000>;
	gpio = <&pio 195 GPIO_ACTIVE_HIGH>;
	enable-active-high;
	/* shared with cam0; keep-alive handled by regulator refcounting
	   only if cam0 uses the same regulator node */
	vin-supply = <&mt6359_vcamio_ldo_reg>; /* if wired so; else drop */
};

cam1_vcamd: regulator-cam1-vcamd {
	compatible = "regulator-fixed";
	regulator-name = "cam1_vcamd";
	regulator-min-microvolt = <1050000>;
	regulator-max-microvolt = <1050000>;
	gpio = <&pio 50 GPIO_ACTIVE_HIGH>;
	enable-active-high;
};

/* inside &i2c4 */
s5k4h7: camera-sensor@2d {
	compatible = "samsung,s5k4h7";
	reg = <0x2d>;

	clocks = <&topckgen CLK_TOP_CAMTG3>;
	clock-names = "mclk";
	assigned-clocks = <&topckgen CLK_TOP_CAMTG3>;
	assigned-clock-rates = <24000000>;

	reset-gpios = <&pio 124 GPIO_ACTIVE_LOW>;

	avdd-supply = <&cam1_vcama>;
	dvdd-supply = <&cam1_vcamd>;
	dovdd-supply = <&mt6359_vcamio_ldo_reg>;

	pinctrl-names = "default";
	pinctrl-0 = <&cam1_mclk_on>;

	port {
		s5k4h7_out: endpoint {
			data-lanes = <1 2 3 4>;
			link-frequencies = /bits/ 64 <700000000>;
			/* remote-endpoint = <&seninf_..._in>; */
		};
	};
};
```

Caveats for the supervisor when wiring this up:

- The driver takes the clock by `devm_v4l2_sensor_clk_get(dev, NULL)`,
  so `clock-names` is optional; `clocks` with CAMTG3 at 24 MHz is
  required (probe fails otherwise). Whether GPIO120/CMMCLK2 pinmux
  needs to be `default` or per-power-state depends on whether the
  `camera_probe` node keeps hogging it — with both enabled, move
  `cam1_mclk_on` to this node and drop it from camera_probe.
- `dvdd` voltage: vendor is 1.05–1.2 V class; stock rails are
  GPIO-switched with no programmable voltage — 1.05 V in the
  fixed-regulator is nominal, measure if possible.
- The `data-lanes = <1 2 3 4>` count is enforced at probe.
