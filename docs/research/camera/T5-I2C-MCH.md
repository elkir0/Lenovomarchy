# T5: Multi-Channel Support in `i2c-mt65xx`

In-tree port of MediaTek MT6785 multi-channel I2C controller support from the Xiaomi `begonia` camera bring-up (`src/begonia-ftp/camera/i2c-mch/mch-port.py` and `src/begonia-ftp/camera/NOTES.md`) into the mainline `i2c-mt65xx` driver for the Lenovo Yoga Tab 11 (`YT-J706F`) camera buses (`&i2c2` and `&i2c4`).

## Background

On the MT6785 SoC, the camera I2C controllers (`i2c2 @ 0x11009000`, `i2c4 @ 0x11011000`, and `i2c7 @ 0x1101a000`; `mt6785.dtsi` L1176, L1253, L1340) are multi-channel hardware blocks whose stock DT assigns `ch_offset_default = <0x100>` (`NOTES.md` L112). Channel 0 (the controller base) is dead for the AP CPU: using mainline `i2c-mt65xx` unmodified causes immediate transfer timeouts with zero interrupts (`NOTES.md` L112).

`begonia` solved this out of tree with `i2c-mt65xx-mch.ko` (generated by `mch-port.py`), using a custom DT property `mediatek,ch-offset = <0x100>`. Task T5 folds the validated behavior into the in-tree `i2c-mt65xx` driver while preserving bit-for-bit identical behavior when `mediatek,ch-offset` is absent or `0`.

## Deliverables

1. `src/mt6785-mainline/drivers/i2c/busses/i2c-mt65xx.c`: optional `mediatek,ch-offset` u32 DT property, register-split accessors (`mtk_i2c_is_shadow`, `mtk_i2c_reg`, `mtk_i2c_readw`, `mtk_i2c_writew`), `mtk_i2c_fifo_clr`, `mtk_i2c_mch_start`, `mtk_i2c_mch_resume`, `mtk_i2c_mch_pio_ok` / `mtk_i2c_mch_pio`, and NACK/timeout handling in `mtk_i2c_do_transfer`.
2. `src/mt6785-mainline/Documentation/devicetree/bindings/i2c/i2c-mt65xx.yaml`: documents `mediatek,ch-offset`.
3. `src/mt6785-mainline/arch/arm64/boot/dts/mediatek/mt6785-lenovo-yt-j706f.dts`: adds `mediatek,ch-offset = <0x100>;` to `&i2c2` (L231) and `&i2c4` (L257). (`&i2c7` is not a camera bus on YT-J706F; see `docs/hardware/BOARD.md` L18-20 and `docs/hardware/CAMERA.md` L13-17.)

### 2. Channel-Specific Control Bits and Sequences

| Mechanism | Details | `begonia` source |
|---|---|---|
| Interrupt routing (`I2C_MCU_INTR_MCH`, `0x40`) | `mtk_i2c_mch_start()` writes `I2C_MCU_INTR_EN_MCH` (`0x0001`) to `base + ch_off + 0x40` right before writing `OFFSET_START` (only when `ch_off != 0`, so `ch_off == 0` / v1 `0x40` = `OFFSET_IO_CONFIG` is never touched). | `mch-port.py` L39-40, L120-123, L303; `NOTES.md` L117 |
| Channel FIFO clear (`I2C_FIFO_ADDR_CLR_MCH`, `0x0004`) | `mtk_i2c_fifo_clr()` writes `I2C_FIFO_ADDR_CLR \| I2C_FIFO_ADDR_CLR_MCH` (`0x0005`) to `OFFSET_FIFO_ADDR_CLR`. | `mch-port.py` L37, L108-110, L288; `NOTES.md` L117 |
| Channel interrupt mask (NACK fix) | `OFFSET_INTR_MASK` enables `I2C_TRANSAC_COMP \| I2C_ARB_LOST \| I2C_BUS_ERR_MCH (1<<8) \| I2C_TIMEOUT_MCH (1<<5)` (plus `restart_flag` if any) and **omits** `I2C_ACKERR` / `I2C_HS_NACKERR`. Enabling `ACKERR` in the channel mask causes the IRQ handler to clear `ACKERR` mid-NACK and jam the channel (`START = 0x3`, `RESUME_ARBIT` stuck); without it in the mask, the `ACKERR` status bit still latches in `OFFSET_INTR_STAT` by the time `I2C_TRANSAC_COMP` fires. | `mch-port.py` L112-118, L180-183, L193-196, L289-290; `NOTES.md` L144-147 |
| Short transfers (`<= 8` bytes) via FIFO PIO | `mtk_i2c_mch_pio()` handles 1-message reads/writes and 2-message write-then-read (`WRRD`) transfers of 1..8 bytes directly via `OFFSET_DATA_PORT` without AP-DMA, re-applying timing/IO config before each transfer and issuing `I2C_TRANSAC_START` only. Mainline's DMA path stalls the channel handshake on short transfers. | `mch-port.py` L245-363 (`mch_pio=true`); `NOTES.md` L116 |
| PIO NACK recovery | On `I2C_HS_NACKERR \| I2C_ACKERR \| I2C_BUS_ERR_MCH \| I2C_TIMEOUT_MCH`, clear only `I2C_FIFO_ADDR_CLR \| I2C_FIFO_ADDR_CLR_MCH` and return `-ENXIO` (no soft reset, no `RESUME_ARBIT`, no `START=0`). | `mch-port.py` L197-199 (`mch_nack_act=0x01`), L321-348; `NOTES.md` L146-148 |
| DMA path (`> 8` bytes / multi-msg) | When `ch_off != 0`: disable `auto_restart` (so `OFFSET_START` receives only `I2C_TRANSAC_START`), run `mtk_i2c_init_hw()` before every transfer (`mch_reinit=true`), clear `INTR_STAT` including `BUS_ERR_MCH \| TIMEOUT_MCH`, clear `INTR_MASK` to `0` after completion, and on NACK with `TRANSAC_COMP && !BUS_ERR_MCH` (`mch_nack_mode=0`) perform `mtk_i2c_fifo_clr()`, write `I2C_RESUME_ARBIT_MCH` (`0x0002`) to channel `OFFSET_START`, warm-reset AP-DMA (`I2C_DMA_WARM_RST`, 10 us, `I2C_DMA_CLR_FLAG`), and return `-ENXIO`. | `mch-port.py` L137-177, L203-214, L233-242; `NOTES.md` L117 |
| Timeout recovery (`mtk_i2c_mch_resume`) | On timeout (or non-`COMP` DMA error), after `mtk_i2c_init_hw()`, write `I2C_RESUME_ARBIT_MCH` (`0x0002`) to `OFFSET_START` in both channel 0 (`base + 0x24`) and the AP channel (`base + ch_off + 0x24`). | `mch-port.py` L86-98, L125-132, L218-219 (`mch_resume_ch=true`), L314-320 |

### Intentionally Omitted (`mch-port.py` Debug/Experiment Leftovers)

- All `module_param` tuning knobs (`mch_debug`, `mch_ackmask`, `mch_nack_act`, `mch_pio`, `mch_reinit`, `mch_nack_mode`, `mch_dma_rst`, `mch_autorestart`, `mch_nack_resume`, `mch_chan`, `mch_resume_ch`, `mch_cfg_both`) — replaced by their validated production defaults.
- `mtk_i2c_mch_dump()` (`dev_info` dump with hardcoded offsets) — mainline `i2c_dump_register()` is already invoked on timeouts and routes through `mtk_i2c_readw()`.
- Custom compatible `"xiaomi,mt6785-i2c-mch"` — in-tree support attaches to standard `"mediatek,mt6785-i2c", "mediatek,mt8186-i2c"` nodes via `mediatek,ch-offset`.

### Note on `ch_off == 0` Invariance

Every register access in `i2c-mt65xx.c` already went through `mtk_i2c_readw()` and `mtk_i2c_writew()`. With `i2c->ch_off == 0`:
- `mtk_i2c_reg()` adds `0` (`mtk_i2c_is_shadow(reg) ? 0 : 0`) to `i2c->base + i2c->dev_comp->regs[reg]`.
- The mirror write in `mtk_i2c_writew()`, `mtk_i2c_mch_resume()`, `mtk_i2c_mch_start()`'s `MCU_INTR` write, `mtk_i2c_mch_pio()` branch, `auto_restart = 0` override, per-transfer `mtk_i2c_init_hw()`, and MCH NACK/error branches are all gated on `if (i2c->ch_off ...)`.
- `mtk_i2c_fifo_clr()` evaluates `I2C_FIFO_ADDR_CLR | 0` and writes `I2C_FIFO_ADDR_CLR`.

## How to Test on the Tablet

1. **Locate the `/dev/i2c-N` devices** for `i2c2` (`i2c@11009000`) and `i2c4` (`i2c@11011000`):

   ```sh
   for d in /sys/class/i2c-dev/i2c-*; do
     echo "$d -> $(readlink -f "$d/device/of_node")"
   done
   ```

2. **Check NACK recovery before powering sensors** (or with a slot powered using `yt11-cam-probe`, see [T1-PROBE.md](T1-PROBE.md)): probe an unpopulated address (e.g., `0x7a`) 3+ times in a row and verify every attempt fails fast with `-ENXIO` (`Remote I/O error` / `No such device or address`), not `-ETIMEDOUT`:

   ```sh
   sudo i2cget -y <N_i2c2> 0x7a 0x00
   sudo i2cget -y <N_i2c2> 0x7a 0x00
   sudo i2cget -y <N_i2c4> 0x7a 0x00
   sudo i2cget -y <N_i2c4> 0x7a 0x00
   ```

3. **Full bus scan with a sensor powered** (`yt11-cam-probe` loaded, `cam0` or `cam1` powered on):

   ```sh
   echo '0 on' | sudo tee /sys/kernel/debug/yt11-cam/power
   sudo python3 tools/camera/cam-id.py <N_i2c2>
   sudo python3 tools/camera/cam-id.py <N_i2c4>
   echo '0 off' | sudo tee /sys/kernel/debug/yt11-cam/power
   ```

   Repeat with `'1 on'` / `'1 off'`. Expected: fast `-ENXIO` on empty addresses and clean chip ID reads on populated addresses, with zero `transfer timeout` messages in `dmesg`.

4. **Check non-MCH buses (`i2c1`, `i2c3`, `i2c5`, etc.)**: confirm fuel gauge (`i2c3` 0x55), MT6360 / backlight (`i2c5`), and light sensor (`i2c1` 0x53) continue working identically.

## Diagnostic Symptoms

| Symptom | Meaning / Likely Cause |
|---|---|
| Every transfer on `i2c2`/`i2c4` hits the 2 s adapter timeout (`-ETIMEDOUT`) with 0 interrupts in `/proc/interrupts` | `mediatek,ch-offset` is missing or `0` (controller is hitting dead channel 0), or `I2C_MCU_INTR_MCH` (`0x40`) was not written before `START`. |
| First transfer passes (or times out), then all subsequent transfers hang until reboot | Configuration registers (`IO_CONFIG`/`TIMING`/`LTIMING`/`HS`/`SOFTRESET`) are not reaching channel 0, AP-DMA is being armed for short transfers instead of PIO, or `auto_restart` (`RS_MUL_TRIG`) is set on the channel. |
| First NACK returns `-ENXIO`, then every later transfer on that bus (even to a valid address) times out (`-ETIMEDOUT`) with `START` stuck at `0x3` | `I2C_ACKERR` / `I2C_HS_NACKERR` was left in `OFFSET_INTR_MASK`, or NACK recovery ran `init_hw` / soft-reset / `RESUME_ARBIT` on the PIO path instead of `FIFO_ADDR_CLR \| FIFO_ADDR_CLR_MCH` only. |
| Timeout only when writing/reading `> 8` bytes (e.g., EEPROM dump) | Issue in the DMA path (`mtk_i2c_do_transfer` with `ch_off != 0`): check `mtk_i2c_init_hw()` per-transfer reinit, `auto_restart = 0`, or DMA warm-reset after NACK. |
| All addresses NACK (`-ENXIO`) quickly without timeouts | I2C controller channel offset is **working**; check sensor power rails, reset polarity, or `CMMCLK` clock/pinctrl (`T1-PROBE.md`). |
