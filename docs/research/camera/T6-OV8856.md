# T6: mainline OV8856 driver with 24 MHz XVCLK support

Task: make `drivers/media/i2c/ov8856.c` in `src/mt6785-mainline` (Linux 7.1,
branch `yt11`) usable on the YT-J706F tablet, whose OV8856 (cam0, identified
2026-11-16, chip ID 0x885a at 0x300b, i2c2 addresses 0x36 and 0x21) is fed
with a 24 MHz master clock from `CLK_TOP_CAMTG2` (see
`docs/hardware/CAMERA.md` and `T1-PROBE.md`).

---

## 1. What mainline has vs what begonia used

Mainline 7.1 `ov8856.c` (2496 lines before this task) is **newer upstream**
than begonia's copy `src/begonia-ftp/camera/ov8856/ov8856.c` (2488 lines).
Begonia did **not** fork the driver for streaming: NOTES.md section M1
(2026-11-13 12:40) says the module was "mainline ov8856.c unchanged",
loaded only to get identification and DT binding; the actual MIPI streaming
(NOTES.md "the real OV8856 over MIPI CSI2") was driven from userspace with
`ov8856-mipi/init.regs` + `vga.regs` over the multi-channel i2c.

Function-by-function comparison (mainline = current tree, begonia = the
copy in `src/begonia-ftp/camera/ov8856/`):

| Area | Mainline 7.1 | Begonia copy | Action |
|---|---|---|---|
| device pointer | `ov8856->dev` cached | `v4l2_get_subdevdata()` everywhere | none (mainline newer) |
| fwnode props (`orientation`, `rotation`) | `v4l2_fwnode_device_parse()` | absent | none |
| xvclk | `devm_v4l2_sensor_clk_get_legacy(dev, "xvclk", false, 0)`: reads `clock-frequency`, sets the rate on OF platforms, falls back to a registered fixed clock | `devm_clk_get` + `clk_set_rate` | none (mainline newer) |
| rate/lane selection | `priv_lane` chosen by lane count only; any rate != 19.2 MHz → `dev_warn` then runs with 19.2 MHz tables | same, plus the same warning | **ported the missing half: selection by rate** |
| mode tables | 19.2 MHz only: `lane_2` (2 modes) and `lane_4` (4 modes), `NUM_MODE_REGS` 187/200 | identical tables | **added 24 MHz set** |
| mode count | `ov8856_modes_num()` walks `supported_modes[]` until `width == 0` — the array is sized 4 and zero-terminated | same | reused as-is (the 24 MHz cfg has 3 real modes) |
| 640x480 mode | none | none (VGA was userspace-only) | **added as a regular mode** |
| power on/off | identical sequence | identical | none |

So the only justifiable port from begonia is the **register data**, not code:
begonia proved on the same SoC that the vendor 24 MHz register sets stream
(2 lanes, 720 Mbps), and that the mainline driver binds and identifies with
a 24 MHz clock while warning.

## 2. Register table origin

All new tables come from the MediaTek vendor driver for the ofilm OV8856
module, `src/begonia-ftp/camera/ref/ov8856ofilm_vendor.c` (extracted from the
begonia vendor partition; `imgsensor_info.mclk = 24`, `mipi_lane_num =
SENSOR_MIPI_2_LANE`). Begonia's `init.regs`/`vga.regs` are verbatim extracts
of the same functions (verified byte-for-byte by script during this task):

| New table (drivers/media/i2c/ov8856.c) | Origin (ov8856ofilm_vendor.c) | Content |
|---|---|---|
| `mipi_data_rate_24mhz_1290mbps[]` (line 224) | PLL regs of `capture_setting()` else-branch (30 fps), function at line 835 | `0x0103` soft reset, `0x0100`=0 standby, `0x0300/0x0302/0x0303/0x030b/0x030c/0x030d`, `0x031e`; MIPI = 1290 Mbps/lane (vendor `mipi_pixel_rate` 258 MHz, 2 lanes) |
| `mipi_data_rate_24mhz_720mbps[]` (line 237) | PLL regs of `preview_setting()` (line 778) — identical in `vga_setting_120fps()` (line 945) | same register set, values for 720 Mbps/lane (vendor `mipi_pixel_rate` 144 MHz, 2 lanes). **This is the PLL that streamed on begonia** (`init.regs` + `vga.regs`) |
| `lane_2_24mhz_mode_3264x2448[]` (line 639) | `sensor_init()` (line 583) body + `capture_setting()` else-branch (30 fps) | 229 regs; hts 1976 / vts 2530 (= vendor `.cap` scenario) |
| `lane_2_24mhz_mode_1632x1224[]` (line 872) | `sensor_init()` + `preview_setting()` | 229 regs; hts 1932 / vts 2482 (= vendor `.pre`/`.slim_video`) |
| `lane_2_24mhz_mode_640x480[]` (line 1105) | `sensor_init()` + `vga_setting_120fps()` (= begonia `vga.regs`) | 229 regs; hts 1932 / vts 620 (= vendor `.hs_video`, 120 fps) |
| `lane_cfg_2_24mhz` (line 2255) | link freqs 645 MHz / 360 MHz (1290/720 Mbps ÷ 2) | 3 modes above |

Registers `0x0100`/`0x0103`/`0x0300/0x0302/0x0303/0x030b/0x030c/0x030d/
0x031e` (stream on/off, soft reset, PLL) are excluded from the mode lists —
they belong to the per-link-frequency PLL lists, applied by
`ov8856_start_streaming()` in the same order the vendor used (PLL list, mode
list, format list, controls, stream on). hts/vts/size values were
cross-checked against `imgsensor_info` (`.pre` linelength 1932/framelength
2482, `.cap` 1976/2530, `.hs_video` 1932/620) — all match.

The 640x480 2-lane mode begonia streamed is ported as a regular mode: same
structure as the others, `link_freq_index = 1` (720 Mbps PLL), 120 fps
capability declared through hts/vts (1932*620 @ pclk 144 MHz ≈ 120 fps).

## 3. Driver changes (what is not table data)

`ov8856_get_hwcfg()` now selects the register set by both lane count and
clock rate:

- `OV8856_XVCLK_19_2` (19.2 MHz): `lane_cfg_2` / `lane_cfg_4` exactly as
  before, any lane count — **nothing changes for 19.2 MHz users**.
- `OV8856_XVCLK_24` (24 MHz): `lane_cfg_2_24mhz` (2 lanes only; the vendor
  module is 2-lane, no 4-lane 24 MHz table exists — probing 4 lanes with a
  24 MHz clock now fails with a clear message instead of silently
  configuring wrong PLLs).
- Any other rate: `-EINVAL` (previously a warning and wrong tables).

Two smaller fixes that the change forced or exposed:
- The `dev_dbg("Using %u data lanes", ...)` read
  `ov8856->cur_mode->data_lanes` **before** `cur_mode` is assigned in
  probe — a NULL dereference on every first probe. Now prints the parsed
  lane count.
- The 19.2 MHz-only `dev_warn` on clock rate was replaced by the hard
  check above (a warning followed by wrong PLL programming was worse than
  useless on this board).

## 4. Config fragment

`kernel/configs/yoga11.config` gains:

```
CONFIG_VIDEO_OV8856=m
```

`CONFIG_VIDEO_CAMERA_SENSOR=y`, `CONFIG_MEDIA_SUPPORT=m`,
`CONFIG_VIDEO_DEV=m`, `CONFIG_MEDIA_CONTROLLER=y`,
`CONFIG_VIDEO_V4L2_SUBDEV_API=y`, `CONFIG_V4L2_FWNODE=m`,
`CONFIG_V4L2_ASYNC=m` and `CONFIG_VIDEO_V4L2_I2C=y` are already set by
`kernel/configs/pmos-mt6785.config` (lines 3809-3838, 4053), which the
fragment is merged on top of. `CONFIG_VIDEO_OV8856` itself sits under
`if VIDEO_CAMERA_SENSOR` in `drivers/media/i2c/Kconfig` (line 675) with no
further dependencies, so the single line suffices.

## 5. DT node the sensor will need (NOT added to the board DT)

Ready-to-paste snippet for `mt6785-lenovo-yt-j706f.dts`, built from the
facts in `docs/hardware/CAMERA.md` (cam0 wiring) and the probe results
(OV8856 on i2c2 at **0x36** first, 0x21 also answers; MCLK GPIO117 =
`CLK_TOP_CAMTG2`; `vcamio` = MT6359 LDO; reset GPIO119 active high in the
stock pin states, but the XSHUTDOWN pin is physically active-low, hence
`GPIO_ACTIVE_LOW` + the driver's existing power sequence):

```dts
/* Root node: supply switches, shared by both cameras */
/ {
	cam0_avdd: cam0-avdd {
		compatible = "regulator-fixed";
		regulator-name = "cam0-avdd";
		regulator-min-microvolt = <2800000>;
		regulator-max-microvolt = <2800000>;
		gpio = <&pio 195 GPIO_ACTIVE_HIGH>;
		enable-active-high;
		pinctrl-names = "default";
		pinctrl-0 = <&cam_avdd_pins>;
	};

	cam0_dvdd: cam0-dvdd {
		compatible = "regulator-fixed";
		regulator-name = "cam0-dvdd";
		regulator-min-microvolt = <1200000>;
		regulator-max-microvolt = <1200000>;
		gpio = <&pio 50 GPIO_ACTIVE_HIGH>;
		enable-active-high;
	};
};

&i2c2 {
	ov8856: camera@36 {
		compatible = "ovti,ov8856";
		reg = <0x36>;

		clocks = <&topckgen CLK_TOP_CAMTG2>;
		clock-names = "xvclk";
		clock-frequency = <24000000>;
		assigned-clocks = <&topckgen CLK_TOP_CAMTG2>;
		assigned-clock-parents = <&topckgen CLK_TOP_UNIVPLL_192M_D8>;

		reset-gpios = <&pio 119 GPIO_ACTIVE_LOW>;
		dovdd-supply = <&mt6359_vcamio_ldo_reg>;
		avdd-supply = <&cam0_avdd>;
		dvdd-supply = <&cam0_dvdd>;

		pinctrl-names = "default";
		pinctrl-0 = <&cam0_mclk_on>;

		port {
			ov8856_out: endpoint {
				remote-endpoint = <&seninf_in>;
				data-lanes = <1 2>;
				link-frequencies = /bits/ 64 <645000000 360000000>;
			};
		};
	};
};
```

Notes for whoever pastes it in:
- `clock-frequency` is deprecated in the binding but still read by
  `devm_v4l2_sensor_clk_get_legacy()` on OF platforms to set the rate;
  `assigned-clock-parents` to `CLK_TOP_UNIVPLL_192M_D8` (24 MHz) does the
  real work and matches what the M0 probe confirmed for GPIO117.
- The `remote-endpoint` and `data-lanes`/`link-frequencies` must be
  reconciled with the SENINF/CAMSV node from T2 once that lands: the
  tablet's CSI-2 port for cam0 is not yet known (begonia: OV8856 on CSI
  port 2 → SENINF4 → MUX2 → CAMSV0); sweep it with `tools/camera/ov-cap.py
  --csi-port 0/1/2`.
- The stock camera-probe node holds `CLK_TOP_CAMTG2` among its clocks and
  `cam0-reset-gpios`/`vcama`/`vcamd` among its GPIOs; when this node lands,
  the probe node must shrink to not double-claim them (out of scope here).
- VCM at i2c2 0x0c (af supply GPIO197) is a separate node, not part of
  this snippet.
