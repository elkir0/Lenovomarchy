## 1. Is there any existing Linux port for the YT-J706F / YT-J706X? (pmOS, Ubuntu Touch/Halium, Droidian, Sailfish, Mobian, custom kernels; Android ROM, device and vendor trees)

### Takeaway
No distribution ships a port for the Yoga Tab 11. pmOS, Ubuntu Touch, Droidian and Sailfish have no device package, page or tree for it. The one piece of real prior art is a **single developer's unpublished pmOS bring-up**, from GitHub user JeremyWildsmith, dated August 2026. He imported Lenovo's GPL 4.14.186 kernel, fixed the build, and got past a post-splash bootloop up to an on-screen framebuffer console. He disabled SSPM to avoid a boot hang. No device package, wiki page or merge request has been published. Android-side trees are minimal: one TWRP tree generated by a tool, using a prebuilt kernel.

### Cited Findings
- **[Confirmed]** The pmOS/Nura wiki has no page for "J706", "Yoga Tab 11", "yoga11" or "MT8789". A full-text API search returns nothing. pmaports has no merge request matching `j706` or `yoga11`. The pmaports `device/` folders (testing, community, main, downstream) hold no `lenovo-yt-j706*` package — [wiki search API](https://wiki.nura.eco/api.php), [pmaports MRs](https://gitlab.nura.eco/nura/pmaports/-/merge_requests)
- **[Confirmed]** `JeremyWildsmith/lenovo-yt-j706f-kernel` was created 2026-08-06 and last pushed 2026-08-06; it has 2 commits and 0 stars. Its initial commit is titled "Initial import: Lenovo Yoga Tab 11 (YT-J706F) GPL kernel source with postmarketOS port fixes". The commit lists these fixes: it disables `CONFIG_TARGET_PROJECT_P522` ("wrongly enabled alongside the correct CONFIG_TARGET_PROJECT_P11", which "pulled in broken eMMC DT nodes"); it fixes a `CONFIG_CUSTOM_KERNEL_LCM` panel name mismatch (`hx83102p_fhdp_dsi_vdo_boe_p522` -> `hx83102p_fhdp_dsi_vdo_boe`), which it calls "the actual root cause of the post-splash bootloop"; it enables `CONFIG_VT`/`CONFIG_FRAMEBUFFER_CONSOLE`; and it fixes a duplicate `set_selection()` — [repo](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel), [commit 0ebf7467fb](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/commit/0ebf7467fb)
- **[Confirmed]** The second commit is titled "Guard SSPM-dependent GPU QoS code with CONFIG_MTK_TINYSYS_SSPM_SUPPORT". Its message says SSPM support "is disabled to avoid a boot hang on postmarketOS, where its firmware/init handshake is never satisfied" — [commit 975d438172](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/commit/975d438172)
- **[Confirmed]** `JeremyWildsmith/lenovo-yt-j706f-toolchain` (2026-08-06) re-hosts `clang-r383902` and `aarch64-linux-android-4.9.1`. **[Claim, by its author]** These are taken "from Lenovo's official GPL kernel source release". clang-r383902 matches the stock kernel's `/proc/version`. The repo exists so the kernel "can be fetched as a build dependency ... via postmarketOS's pmaports". "The kernel does **not** build cleanly with a generic/system Clang + cross-binutils combination (toolchain mismatches were the root cause of the majority of early build failures)" — [toolchain README](https://github.com/JeremyWildsmith/lenovo-yt-j706f-toolchain)
- **[Confirmed]** The same author has an earlier repo, `JeremyWildsmith/android_linux_lenovo_yoga11` (created 2024-12-13, last push 2024-12-31). It holds a Linux **4.14.186** tree with `yoga11_defconfig`, `yoga11_lte_defconfig`, `yoga11.dts` and `yoga11_lte.dts`; the LTE files cover the YT-J706X. It also carries MediaTek reference-board configs (tb8185p3, tb8788p1, tb8789p1, tb8797p1, ...) — [repo](https://github.com/JeremyWildsmith/android_linux_lenovo_yoga11)
- **[Confirmed]** Android device tree `JeremyWildsmith/android_device_lenovo_yoga11` (created 2024-12-10, last push 2024-12-10, 0 stars). It is generated with "SebaUbuntu's TWRP device tree generator" and uses a **prebuilt kernel** (`TARGET_FORCE_PREBUILT_KERNEL := true`). `BoardConfig.mk` shows: A/B (`AB_OTA_UPDATER`), `BOARD_USES_RECOVERY_AS_BOOT`, boot header v2, `BOARD_KERNEL_BASE 0x40078000`, ramdisk offset `0x07c08000`, tags offset `0x0bc08000`, page size 2048, cmdline `bootopt=64S3,32N2,64N2 buildvariant=user`, platform `mt6785`, a ~9.1 GB super partition (system/vendor/product), AVB on with vbmeta `--flags 3`, vendor security patch 2021-08-01, and partition sizes `BOARD_BOOTIMAGE_PARTITION_SIZE := 33554432` (32 MiB) — [BoardConfig.mk](https://github.com/JeremyWildsmith/android_device_lenovo_yoga11/blob/master/BoardConfig.mk)
- **[Confirmed]** `yungvender/android_device_Lenovo_YT-J706F` ("Device tree for Lenovo Yoga Tab 11 (YT-J706F, WiFi Version)", 2025-09-10) is an **empty** repository — [repo](https://github.com/yungvender/android_device_Lenovo_YT-J706F)
- **[Confirmed]** Naming trap: **TB-J706F is a different tablet**, the Lenovo Tab P11 Pro (Qualcomm SM7150). Several GitHub trees, a Lenovo kernel drop and XDA threads refer to TB-J706F. Likewise, pmOS `linux-lenovo-q706f` targets SM8250. None of these apply to the YT-J706F — [HK4567/android_kernel_lenovo_sm7150](https://github.com/HK4567/android_kernel_lenovo_sm7150), [XDA "Android R Kernel for Lenovo TB-J706F"](https://xdaforums.com/t/android-r-kernel-for-lenovo-tb-j706f.4410027/)
- **[Confirmed]** Stock firmware packages are named for MT6785, e.g. `Lenovo_Yoga_Tab_11_YT-J706F_MT6785_USR_S240127_...`; a later build is `S240301_240918_ROW` — [firmwarefile.com](https://firmwarefile.com/lenovo-yoga-tab-11-yt-j706f)
- **[Confirmed]** An XDA thread "[Root Guide] YT-J706F Lenovo Yoga Tab 11" exists, but I could not read it (HTTP 403) — [XDA](https://xdaforums.com/t/root-guide-yt-j706f-lenovo-yoga-tab-11.4463519/)
- **[Confirmed]** I found no Droidian port for this tablet or for any MT6785 device. The `droidian-devices` GitHub org has no MT6785, Lenovo-MTK or "yoga" repository. `rifux/droidian-begonia` (2024-09-12) is only a copy of the generic Droidian images README — [rifux/droidian-begonia](https://github.com/rifux/droidian-begonia)

### Inferences
- The JeremyWildsmith work is the closest prior art, and it confirms that route (b) boots to at least a framebuffer console on this exact tablet. The fix list contains no Wi-Fi, audio, GPU or suspend work. With SSPM disabled, power management is likely degraded (see question 4). The work appears to have paused after 2026-08-06; no later pushes exist.
- The device-tree boot offsets are identical to the Redmi Note 8 Pro's pmOS deviceinfo (base 0x40078000, ramdisk 0x07c08000, tags 0x0bc08000; see question 2). The MT6785 LK conventions therefore carry over directly.
- With a 32 MiB boot partition, an Arch-style initramfs must stay small. That matters more under A/B with recovery-as-boot.

### Gaps
- Unlock procedure, anti-rollback and vbmeta behaviour on the YT-J706F: the XDA thread was unreadable (403).
- Whether JeremyWildsmith got anything beyond the fbcon, e.g. USB networking, touch or a userspace. No device package or pmaports fork is public, so I could not check.
- LineageOS/AOSP ROMs: I found no LineageOS, crDroid or GSI-specific tree or vendor tree for the YT-J706F; an XDA search was not possible.

## 2. Linux ports to other MT6785 (Helio G90/G90T/G95) devices: which distribution, mainline or downstream, what works, what blocked them

### Takeaway
There are three meaningful MT6785 Linux efforts, all on phones:
- **pmOS Redmi Note 8 Pro (xiaomi-begonia)**. A downstream 4.14 port ran from 2021 to 2025 and only reached screen, touch, USB networking and OTG; Wi-Fi, audio, Bluetooth, 3D and battery were **not** working. It was archived in Sept. 2025 in favour of a **mainline** port (6.16.4, a 7.1 branch in progress), where Panfrost 3D works but Wi-Fi, audio, Bluetooth and battery are still missing.
- **pmOS Redmi Note 10S (xiaomi-rosemary)**: downstream 4.14.340, same picture.
- **Ubuntu Touch on begonia**. This Halium 10 port on kernel 4.14.141 is the only MT6785 Linux port with Wi-Fi, Bluetooth, audio, camera, modem and GPU working. It is actively maintained (last commit 2026-10-10, stable 24.04-1.4) because it keeps Android's HALs inside a container through libhybris.

### Inferences
- Across five years of MT6785 work, **every port that ran a plain Linux userspace on a downstream 4.14 kernel stalled at display, touch and USB**. Wi-Fi, audio, Bluetooth, 3D and battery were never made to work. The only port with full hardware support (UT) works because it runs Android's vendor stack (WMT launcher, audio HAL, gralloc/hwcomposer, Mali EGL) in a Halium container. It does not replace that stack.
- The pmOS community itself abandoned the downstream MT6785 route for mainline in 2025. On the mainline side, 3D works (Panfrost), while Wi-Fi, audio and battery are still open.
- `AgentFabulous/begonia` carries in-tree CONSYS drivers (wlan/bt/gps/fm) for the same SoC. That makes it a candidate donor if the Lenovo GPL drop lacks them (see question 3).

### Gaps
- No feature tables exist for Realme 6 / Narzo / Realme 7 (MT6785), Infinix or Tecno G90T/G95 Linux ports. I found no Linux port for them, only Android trees.
- The rosemary UT port's status is unknown (404).

## 3. Lenovo kernel source for the YT-J706F: is it published, for which firmware, how complete, does it build?

### Takeaway
A Lenovo GPL kernel drop for the YT-J706F exists, but I could not locate it on Lenovo's portal. One developer re-hosted it (4.14.186, `yoga11_defconfig` and `yoga11_lte_defconfig`, with Lenovo's clang-r383902 toolchain), and it builds once fixed. It is **incomplete by construction**. MediaTek's connectivity drivers (Wi-Fi/BT/GPS/FM) are not in the tree; the defconfig has them commented out, so they were out-of-tree modules on the vendor side. The defconfig also shipped with wrong project and panel selections. A GPL request for the **current** Android 12 build (`S240301_240918_ROW`, kernel `4.14.186-g59da9ac88f6c`) has been open on Lenovo's GitHub since 2026-10-31 with no answer.

### Cited Findings
- **[Confirmed]** Issue lenovo/gplcc #23, "GPL Kernel Source Request – Lenovo Yoga Tab 11 YT-J706F", opened 2026-10-31, still open, no comments. It asks for the source of firmware `YT-J706F_S240301_240918_ROW`, kernel `4.14.186-g59da9ac88f6c`, Android 12, codename `yoga11`. The `lenovo/gplcc` repo itself has had no push since 2020-08-06, and none of its 25 issues (2022–2026) have been answered with a release — [issue #23](https://github.com/lenovo/gplcc/issues/23), [issue list](https://github.com/lenovo/gplcc/issues)
- **[Claim, by the re-hoster]** The toolchain and kernel come from "Lenovo's official GPL kernel source release for the Yoga Tab 11 (YT-J706F, MediaTek MT6785/MT8789)" — [toolchain README](https://github.com/JeremyWildsmith/lenovo-yt-j706f-toolchain)
- **[Confirmed]** The kernel version is 4.14.186 ("Petit Gorille"), matching the stock kernel version string. MediaTek `build.config.mtk.aarch64*` files are present — [Makefile](https://github.com/JeremyWildsmith/android_linux_lenovo_yoga11/blob/master/Makefile)
- **[Confirmed] Contents of `yoga11_defconfig` (458 lines)**:
  - Display: `CONFIG_MTK_PLATFORM="mt6785"`, `CONFIG_MTK_FB=y`, `CONFIG_MTK_LCM=y`, `CONFIG_CUSTOM_KERNEL_LCM="hx83102p_fhdp_dsi_vdo_boe nt36523w_fhdp_dsi_vdo_boe"` (two panel sources), `CONFIG_LCM_WIDTH="1200"`, `CONFIG_LCM_HEIGHT="2000"`, `CONFIG_MTK_LCM_PHYSICAL_ROTATION="180"`; no `CONFIG_DRM_MEDIATEK`.
  - GPU: `CONFIG_MTK_GPU_VERSION="mali bifrost r25p0"`.
  - Connectivity is all commented out: `#CONFIG_MTK_COMBO=y`, `#CONFIG_MTK_COMBO_CHIP_CONSYS_6785=y`, `#CONFIG_MTK_COMBO_WIFI=y`, `#CONFIG_MTK_COMBO_BT=y`, `#CONFIG_MTK_BTIF=y`; `CONFIG_CFG80211=y`.
  - Power and charging: `CONFIG_MTK_TINYSYS_SSPM_SUPPORT=y` (v1), `CONFIG_MT6360_PMU_CHARGER=y`, `CONFIG_MTK_CHARGER=y`, `CONFIG_MTK_GAUGE_VERSION=30`.
  - Audio: `CONFIG_SND_SOC_MT6785_MT6359=y`, `CONFIG_SND_SOC_CS35L41=y`, `CONFIG_SND_SOC_AS33970=y`.
  - Touch: Himax HX83102 in-cell and NT36xxx SPI.
  - Android pieces: `CONFIG_ION=y`/`CONFIG_MTK_ION=y`, RNDIS/ACM configfs gadgets, pstore RAM.
  - Also: `# CONFIG_FHANDLE is not set`, `# CONFIG_VT is not set`, `CONFIG_TARGET_PROJECT_P530=y`.
  — [yoga11_defconfig](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/blob/HEAD/arch/arm64/configs/yoga11_defconfig)
- **[Confirmed]** Drivers present in the tree:
  - Panels: `drivers/misc/mediatek/lcm/hx83102p_fhdp_dsi_vdo_boe`, `nt36523w_fhdp_dsi_vdo_boe`, plus `_p522` and INX variants; backlight/bias drivers `KTZ8864A`, `OCP2138`, `SGM37604A`.
  - Touch: `drivers/input/touchscreen/mediatek/hxchipset_hx83102p`, `hxchipset_p11`, `NT36xxx_p11`.
  - Display: the legacy MTK stack `drivers/misc/mediatek/video/mt6785/{dispsys,videox}` (`mtkfb.c`, `primary_display.c`, `mtk_disp_mgr.c`, `mtkfb_fence.c`).
  - GPU: Mali kbase versions `mali-r14p0` … `mali-r25p0` under `gpu_mali/mali_bifrost`, plus `ged`.
  - Connectivity: `drivers/misc/mediatek/connectivity` contains **only `common` and `power_throttling`**; no wlan, bt, gps or fm. `btif`, `conn_md` and `ccci` are present.
  — [kernel tree](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/tree/HEAD/drivers/misc/mediatek)
- **[Confirmed]** `yoga11.dts` (2259 lines) declares:
  - the boot LCM `hx83102p_fhdp_dsi_vdo_boe_drv`;
  - `hid-over-i2c` devices;
  - fuel gauge `ti,bq27541` alongside `mediatek,charger`;
  - SAR sensors `awinic,aw9610x_sar` (firmware "aw9610x_wifi"), `abov` and `Semtech,sx933x`;
  - a `syna,as33970` codec/DSP;
  - **four `cirrus,cs35l41` smart amps** at 0x40–0x43, each needing `cs35l41-dsp1-spk-prot.wmfw` and `cs35l41-dsp1-spk-cali.wmfw` plus per-amp `.bin` tuning files.
  — [yoga11.dts](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/blob/HEAD/arch/arm64/boot/dts/mediatek/yoga11.dts)
- **[Confirmed]** The tree's downstream MediaTek **DRM** driver (`drivers/gpu/drm/mediatek/mtk_drm_drv.c`, 4129 lines) has match data for mt2701, mt2712, mt6779, mt6781, mt6833, mt6853, mt6873, mt6877, mt6885 and mt8173, and **no mt6785** (0 occurrences) — [mtk_drm_drv.c](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/blob/HEAD/drivers/gpu/drm/mediatek/mtk_drm_drv.c)
- **[Confirmed]** Build status: the re-hosted tree builds only with Lenovo's clang-r383902 and GCC 4.9.1 binutils, after the config fixes listed in question 1 — [toolchain README](https://github.com/JeremyWildsmith/lenovo-yt-j706f-toolchain), [commit 0ebf7467fb](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/commit/0ebf7467fb)
- **[Claim, search summary]** Lenovo has historically published tablet kernel tarballs through support.lenovo.com "Open Source Code" downloads (e.g. IdeaTab A1000L, `ds036947`). The Lenovo Open Source Portal page (HT511330) returned HTTP 403 to my fetch — [Lenovo A1000L example](https://support.lenovo.com/ph/en/downloads/ds036947-open-source-code-kernel-ideatab-a1000l-tablet), [Lenovo Open Source Portal](https://pcsupport.lenovo.com/us/zc/solutions/HT511330)

### Inferences
- The defconfig's commented-out `MTK_COMBO_*` lines, together with an in-tree `connectivity/` holding only `common`, match the Android 10+ MediaTek layout. There, `wmt_drv.ko`, `wmt_chrdev_wifi.ko`, `wlan_drv_gen4m.ko`, `bt_drv.ko` and similar are built from `vendor/mediatek/kernel_modules/connectivity` and shipped on the vendor partition. Wi-Fi on route (b) therefore needs one of three things: (i) those module sources, if Lenovo's tarball includes `vendor/mediatek/kernel_modules` (unverified); (ii) a transplant from another MT6785 4.14 tree such as `AgentFabulous/begonia`, which has them in-tree; or (iii) the stock vendor `.ko` files. Option (iii) only loads on a kernel with the exact stock vermagic and symbol CRCs, which means keeping the stock kernel.
- The tree builds the same driver set for the YT-J706X (`yoga11_lte_*`), so the X variant (CCCI/modem) is covered by the same source.
- The fact that the panel and project selection had to be corrected suggests that the published defconfig does not reproduce the shipped `4.14.186-g59da9ac88f6c` build exactly. The open gplcc request is consistent with that. Expect "close but not identical" source, the typical incomplete GPL drop.
- Audio on this tablet is complex even by MTK standards: 4× CS35L41 with DSP firmware and calibration, plus an AS33970. On Android, speaker protection and calibration are driven by vendor HAL and "smartpa" logic, which a plain ALSA setup would have to reproduce.

### Gaps
- Exact download location, date and firmware version of Lenovo's official YT-J706F tarball. Lenovo's portal was unreachable (403), and the re-hoster does not give a URL.
- Whether the tarball includes `vendor/mediatek/kernel_modules` (connectivity, possibly `met`, `fpsgo`), DTBO sources or a full build script.
- Whether the Mali r25p0 kbase in the tree matches the userspace `libGLES_mali.so` on the Android 12 vendor image. MTK sometimes updates the vendor blob independently of the kernel drop.

## 4. Route (b) in detail: a non-Android userspace (Arch Linux ARM + Hyprland) on the MTK 4.14 downstream kernel

### Takeaway
Route (b) delivers boot, a framebuffer console, touch and USB gadget networking quickly; one person already reached the console on this tablet. Every piece Omarchy actually needs is then blocked or expensive:
- **Display:** the MT6785 4.14 stack is fbdev (`mtkfb`) with no DRM/KMS, and Hyprland's backend library (aquamarine) supports only DRM/KMS, nested Wayland and headless.
- **GPU:** acceleration is only possible through the bionic Mali blob via libhybris; Panfrost needs a ≥5.x kernel driver, and the kbase-based Panfork is dead.
- **Wi-Fi, BT and audio:** these need Android's vendor daemons and HALs (Halium-style) or substantial reimplementation.
- **systemd:** Arch Linux ARM's systemd 262 officially requires kernel ≥ 5.10, and the compatibility code for older kernels has been removed.

### Cited Findings
**Display**
- **[Confirmed]** MT6785 on this kernel uses the legacy fbdev display stack (`video/mt6785/videox/mtkfb.c`, `primary_display.c`, `mtk_disp_mgr.c`) with `CONFIG_MTK_FB=y`. The in-tree downstream DRM driver has no mt6785 support (see question 3) — [videox dir](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/tree/HEAD/drivers/misc/mediatek/video/mt6785/videox)
- **[Confirmed]** Aquamarine, Hyprland's rendering backend since Hyprland PR #6608 (2024), lists only a Wayland backend, a DRM backend (KMS/libinput) and a virtual/headless backend. Hardware-plane support is still unchecked, and there is no fbdev or hwcomposer backend — [aquamarine README v0.4.4](https://code.hyprland.org/hyprwm/aquamarine/raw/tag/v0.4.4/README.md), [Arch wiki: Hyprland](https://wiki.archlinux.org/title/Hyprland)
- **[Confirmed]** The pmOS downstream begonia port reported "screen Y" and "Xwayland Y", but "3D N", on 4.14 (my reading: software rendering on the framebuffer) — [wiki rev 82242](https://wiki.nura.eco/index.php?oldid=82242)
- **[Confirmed]** Droidian's graphics stack is phoc/phosh on **wlroots with a hwcomposer backend**, which uses libhybris to reach Android's HWC2. Snapshot 99 shipped wlroots 0.17.4 "with various improvements to the hwcomposer backend". An older pmOS MR to package wlroots with the hwc2 backend said that "theoretically, this should be enough to run Phosh or Sway on devices that use Halium" — [Droidian releases](https://github.com/droidian-images/droidian/releases), [State of Droidian wk32-2022](https://droidian.org/blog/state-of-droidian-week-32-2022/), [pmaports MR 1463](https://gitlab.com/postmarketOS/pmaports/-/merge_requests/1463)

**GPU**

Panfork (`gitlab.com/panfork/mesa`) ran Panfrost on top of kbase, but its README now says only "Use upstream instead", and the project has been inactive since 2024-08-10 — [Collabora: overview of Panfrost](https://www.collabora.com/news-and-blog/blog/2019/03/13/an-overview-of-the-panfrost-driver/), [panfork/mesa](https://gitlab.com/panfork/mesa), [Radxa Panfork doc](https://docs.radxa.com/en/rock3/rock3b/app-development/panfork)

**Wi-Fi / Bluetooth**
- **[Confirmed]** The pmOS wiki says MediaTek Wi-Fi devices "are much more complicated to get working". Android starts `wmt_loader`/`6620_loader`, and `6620_launcher` "(probably) loads the firmware". ### Inferences
- **Hyprland cannot run on the stock MT6785 4.14 display stack as-is**: there is no KMS, and aquamarine has no fbdev or hwcomposer backend. There are three ways out, each a project in itself:
  1. Port mt6785 into the tree's downstream `mtk_drm` driver. It already covers the sibling mt6779 (Helio P90), which is the closest template; this is a kernel-side task of uncertain size. Hyprland then still needs EGL/GBM.
  2. Write a hwcomposer (HWC2 via libhybris) backend for aquamarine, comparable to Droidian's wlroots hwcomposer backend. That code would be an out-of-tree fork of Hyprland's backend library, which would then have to be maintained.
  3. Write a tiny KMS shim over `mtkfb`, a dumb-buffer DRM driver that blits to the framebuffer. It would give KMS but no GPU, so Hyprland would render in software (pixman/llvmpipe) at 2000×1200.
- **The GPU on route (b) is libhybris-only.** Hyprland also needs GBM/dmabuf buffer sharing, which the bionic Mali blob does not provide natively; Halium uses Android gralloc instead. Expect Hyprland + libhybris to need the same kind of glue Droidian wrote for wlroots, and no one has published it. Panfrost on 4.14 would require backporting the upstream panfrost DRM driver plus DRM scheduler and io-pgtable dependencies, which is not realistic. Panfork is abandoned.
- **Wi-Fi, BT and audio without Android** means rebuilding the WMT stack (out-of-tree modules plus a launcher protocol reimplementation) and writing ALSA UCM for MT6359 + 4× CS35L41 + AS33970, with no published MT6785 success to copy. The pragmatic version of route (b) is the Halium model: keep `/vendor` and an Android LXC container running the HALs (wmt_loader/launcher, audio HAL, sensors, hwcomposer). That is a different architecture from Omarchy's.
- **systemd is a hard blocker for "plain Arch Linux ARM"**. ALARM's systemd 262 is two baselines beyond 4.14, with the compatibility code removed. The options are:
  - pin systemd ≤257 (a frozen, diverging package set, and Omarchy's user services and logind expectations would need checking);
  - switch to a non-systemd init (OpenRC/dinit) and use seatd for Hyprland;
  - backport syscalls into 4.14 (unrealistic at that scale).
  Glibc is fine (`--enable-kernel=4.4`). pacman needs `DisableSandbox`. Landlock and io_uring are absent, and cgroup2's cpu controller is absent (4.15). The kernel config also needs `FHANDLE`, `DEVTMPFS`, `AUTOFS` and namespaces turned on (to be verified).
- Net assessment: route (b) is cheap up to "console on screen" (days, already demonstrated). It becomes the most expensive route for a usable Omarchy (GPU-accelerated Hyprland, Wi-Fi, audio, suspend), because every subsystem has to be re-done against Android-only vendor interfaces on a kernel that current Arch userspace no longer supports.

### Gaps
- Whether Lenovo's tarball carries `vendor/mediatek/kernel_modules/connectivity`. This decides whether route (b) Wi-Fi is a build job or a port.
- Whether any project has run Hyprland/aquamarine on libhybris. My searches found none.
- Real systemd 257 vs 262 behaviour on an Android 4.14 kernel; I did not test this and found no report.
- MT6785 deep-idle and suspend behaviour on a non-Android userspace with SSPM disabled vs enabled. I found no measurement.
- Whether Arm's official Linux (non-Android) Mali Bifrost userspace (fbdev/Wayland/GBM builds), or Rockchip `libmali-bifrost`, can drive a G76 on kbase r25p0. Unverified.

## 5. Lessons from these projects that change the plan

### Takeaway
The prior art points away from route (b) as a path to a full Omarchy and towards using it, at most, as a short-lived bring-up and recovery tool. Five years of MT6785 downstream ports never achieved Wi-Fi, audio or 3D without Android's stack. pmOS deliberately switched MT6785 to mainline, where Panfrost works and Wi-Fi, audio and battery are the open items. Several boot-chain lessons from begonia and the YT-J706F bring-up carry over directly.

### Cited Findings
- **[Confirmed]** pmOS archived the downstream begonia port and replaced it with mainline in 2025-09 (MR !6975). The mainline kernel line is still advancing (7.1 branch 2026-06-17, draft MR !8852) — [MR !6975](https://gitlab.nura.eco/nura/pmaports/-/merge_requests/6975), [mt6785-mainline/linux](https://gitlab.nura.eco/mt6785-mainline/linux)
- **[Confirmed]** MT6785 boot-chain lessons from begonia:
  - The stock LK ignores a mainline DTB, so uniLoader is needed as a second stage, or a custom minimal DTBO.
  - The bootloader needs an (empty) DTBO image.
  - The stock bootloader's cmdline injection must be neutralised.
  - Flash vbmeta if the device bootloops.
  - mtkclient (`mtk da seccfg unlock`) works for unlock and unbrick through BROM.
  — [wiki rev 82242](https://wiki.nura.eco/index.php?oldid=82242), [begonia wiki](https://wiki.nura.eco/wiki/Xiaomi_Redmi_Note_8_Pro_(xiaomi-begonia)), [device APKBUILD](https://gitlab.nura.eco/nura/pmaports/-/blob/main/device/testing/device-xiaomi-begonia/APKBUILD)
- **[Confirmed]** YT-J706F lessons from the downstream bring-up:
  - The vendor defconfig can select the wrong project and panel; the result was a post-splash bootloop.
  - SSPM hangs boot without Android's init handshake.
  - The vendor toolchain (clang-r383902 + GCC 4.9.1 binutils) is required to build.
  — [commit 0ebf7467fb](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/commit/0ebf7467fb), [commit 975d438172](https://github.com/JeremyWildsmith/lenovo-yt-j706f-kernel/commit/975d438172), [toolchain README](https://github.com/JeremyWildsmith/lenovo-yt-j706f-toolchain)
- **[Confirmed]** MediaTek Wi-Fi on downstream kernels is a recurring blocker across pmOS: only one MediaTek device in pmaports has working Wi-Fi — [Nura wiki: WiFi](https://wiki.nura.eco/wiki/WiFi)
- **[Confirmed]** The Halium approach (UT begonia) is the only MT6785 Linux system with working Wi-Fi, BT, audio, camera and GPU. Even so, the microphone and RTC were still broken in late 2026 — [devices.ubuntu-touch.io](https://devices.ubuntu-touch.io/device/begonia)
- **[Confirmed]** Lenovo has not answered any GPL request on its GitHub compliance tracker since 2022 (25 open or closed issues, no releases) — [lenovo/gplcc issues](https://github.com/lenovo/gplcc/issues)

### Inferences
- **Plan change 1:** treat route (b) as a *tool*, not the product. The stock or GPL 4.14 kernel plus a tiny initramfs is useful early on. It provides fbcon, USB RNDIS (`CONFIG_USB_CONFIGFS_RNDIS=y` is already set) and pstore RAM (`CONFIG_PSTORE_RAM=y` is set). With them, the team can dump the panel init sequences, regulator and GPIO state, CS35L41 firmware, the WMT/CONSYS firmware and Android `init.*.rc` files from a running, known-good kernel. That data feeds the mainline DTS. The tablet has no UART, so a kernel known to bring up fbcon + pstore + RNDIS is a valuable debug channel.
- **Plan change 2:** for the product, reuse the MT6785 mainline effort (`mt6785-mainline/linux` 7.1, uniLoader, Panfrost already working on G76 MC4). The Yoga-specific work is then the panel (HX83102P or NT36523W, two vendors), touch (Himax/Novatek SPI), the MT6360 charger and bq27541 gauge, CS35L41 ×4 (mainline has a CS35L41 driver; firmware comes from the vendor image) and CONSYS Wi-Fi/BT. The last item is the hardest and the one that mainline begonia has not solved either (its wiki says "Technically possible").
- **Plan change 3:** if, after mainline evaluation, the team still wants route (b) for a fast usable device, the realistic form is Halium-style: keep Android's vendor partition and an LXC container, and use a wlroots-hwcomposer compositor (phoc/Sway) rather than Hyprland. Accept a pinned older systemd or a Debian/Ubuntu base (Droidian/UT style) rather than current Arch Linux ARM. That would no longer be "Omarchy" in the Hyprland/Arch sense.
- **Plan change 4:** budget for two panel and touch variants. The kernel lists BOE HX83102P and BOE NT36523W, plus `_p522`/INX variants, in `CONFIG_CUSTOM_KERNEL_LCM`. Lenovo tablets ship mixed panels, as begonia does (CSOT/Tianma split in MR !8852).
- **Plan change 5:** before writing any code, check whether Lenovo's tarball includes connectivity module sources. If it does not, start from `AgentFabulous/begonia`'s in-tree `connectivity/{wlan,bt,gps,fmradio}`.

### Gaps
- No public report quantifies effort or time-to-feature for a Halium port of an MT6785 *tablet*; UT begonia is a phone, and its timeline runs 2021 to 2026.
- Whether the YT-J706F's LK enforces the same DTB/DTBO behaviour as begonia's, and whether uniLoader would work on it, is untested; the bootloader unlock path is unconfirmed because XDA was unreadable.
